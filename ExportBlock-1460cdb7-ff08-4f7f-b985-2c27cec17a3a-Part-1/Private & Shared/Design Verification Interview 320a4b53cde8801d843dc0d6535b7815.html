    input logic [15:0]                in_data,

    output logic                      out_trigger,
    output logic [31:0]               out_header
);

    localparam logic [23:0] MATCH_DATA_1 = 24'hDF0132;
    localparam logic [23:0] MATCH_DATA_2 = 24'h4DE91B;
    localparam logic [23:0] MATCH_DATA_3 = 24'h73AC06;
    localparam logic [23:0] MATCH_DATA_4 = 24'hA1C47D;

    // We have incoming data packets with 32 bits each. I notices something here:
    // 1. If we have matching sequence, out_triggered is HIGH, out_valid is HIGH,
    //    the out_header follows {NEWEST,...,OLDEST} order.
    
    typedef enum [2:0] {IDLE, MATCH1, MATCH2, MATCH3, MATCH4} state_t;
    logic [15:0] in_data_d;
    reg [31:0] in_data_reg [0:3];
    logic [31:0] tmp_header;
    logic [7:0] counter;
    
    state_t state;

        if(reset) begin
            state <= IDLE;
            counter <= 0;
            for (int i = 0; i < 4; i++) begin
                in_data_reg[i] <= 32'd0;
            end
        end else begin

            in_data_d <= in_data;
            counter <= (in_data !=0 && in_data != in_data_d) ? ((counter < 7) ? counter + 1 : 0) : counter;       // Counter indicate the number of packet from input

                    in_data_reg[i] <= 32'd0;
                end

  1. UVM Question:

    How do sequences and drivers interact? Say if we have two forked sequences generated by user with

    fork
	s1.start() // s1 last for 10 cycles

	s2.start() // s2 last for 20 cycles
join

    Is it possible to determine which packet start first? When will the packet finish processing, 20 cycles or 30 cycles? Does one process needs to wait until the other to finish?

    ChatGPT answer:

    • s1.start() and s2.start() are launched concurrently by the fork...join.
    • If both sequences run on the same sequencer/driver, then only one item/transaction is driven at a time.
    • So:
      • Which starts first at the sequence level? Both are started concurrently.
      • Which gets to the driver first? Not deterministically guaranteed unless you set arbitration/priority.
    • Does one need to wait for the other sequence to completely finish?

      No. It does not need to wait for the whole other sequence to finish. It only waits when competing for the sequencer/driver.

    • Total finish time: 20 or 30 cycles?
      • If by “10 cycles” and “20 cycles” you mean each sequence holds the shared driver exclusively for that entire duration, then total is effectively 30 cycles.
      • If they are just independent threads not contending for the same driver resource, then it could complete in 20 cycles.
      • In the usual same sequencer/same driver case, answer is 30 cycles, not 20.
    • So the clean practical answer for normal UVM shared-driver case is:
      • Order first: not guaranteed
      • Total time: 30 cycles
      • Wait behavior: they start together, but one waits for access to the shared sequencer/driver while the other is using it

class Solution(object):
    def reverseList(self, head):
        """
        :type head: Optional[ListNode]
        :rtype: Optional[ListNode]
        """
        curr = head
        prev = None

        while (curr):
            nxt = curr.next
            curr.next = prev
            prev = curr
            curr = nxt

        return prev

#         self.val = val
#         self.next = next
class Solution(object):
    def reorderList(self, head):
        """
        :type head: Optional[ListNode]
        :rtype: None Do not return anything, modify head in-place instead.
        """
        slow, fast = head, head.next
        while fast and fast.next:
            slow = slow.next
            fast = fast.next.next
        
        second = slow.next
        prev = slow.next = None
        while second:
            tmp = second.next
            second.next = prev
            prev = second
            second = tmp

        first, second = head, prev
        while second:
            tmp1, tmp2 = first.next, second.next
            first.next = second
            second.next = tmp1
            first, second = tmp1, tmp2

Randomization

When a rand item is defined and we call .randomize(), we can define a post_randomize() function which executes automatically after each randomization call.

class randframe;
  local string name;
  rand local bit [3:0] length;
  bit [7:0] payload[];

  function new(string name);
    this.name = name;
  endfunction

  function void post_randomize();
    payload = new[length];
    foreach (payload[i]) payload[i] = $urandom;
  endfunction
endclass

Simulation Phases

All phase methods take single uvm_phase phase argument. All phases except run_phase are functions (zero-time). run_phase is a task (consumes time). build_phase MUST call super.build_phase(phase) first.

Phase Order

build → connect → end_of_elaboration → start_of_simulation → run → extract → check → report → final

Run-Time Sub-Phases

Sub-phases run in parallel with run_phase, executing in order:

pre_reset → reset → post_reset → pre_configure → configure → post_configure → pre_main → main → post_main → pre_shutdown → shutdown → post_shutdown

A UVC can run stimulus in reset_phase while another runs in main_phase — they overlap with run_phase. The phase scheduler waits for all UVCs to complete a sub-phase before advancing.

virtual function void build_phase(uvm_phase phase);
  super.build_phase(phase); // MUST be first — applies config settings
endfunction

virtual task run_phase(uvm_phase phase); // task, not function
  forever begin
    seq_item_port.get_next_item(req);
    drive_packet(req);
    seq_item_port.item_done();
  end
endtask

Sequences

Sequence Structure

Sequences are data objects (not components): uvm_object_utils, data constructor (name), stimulus defined in body() task.

class yapp_seq extends uvm_sequence #(yapp_packet);
  // Type param defines built-in handle: yapp_packet req;
  `uvm_object_utils(yapp_seq)

  function new(string name = "yapp_seq");
    super.new(name);
  endfunction

  virtual task body();
    `uvm_info(get_type_name(), "Call yapp_seq", UVM_LOW)
    `uvm_do(req)                        // 1 random packet
    `uvm_do_with(req, {addr == 0;})     // 1 packet constrained to addr=0
  endtask
endclass

`uvm_do Macro — 7 Steps

Step 1: factory create → Step 2: synchronize with sequencer (start_item) → Step 3: pre_do() hook → Step 4: randomize → Step 5: mid_do() hook → Step 6: send item, wait item_done (finish_item) → Step 7: post_do() hook

Macro variants:

  • uvm_do(req) ` — all 7 steps
  • uvm_do_with(req, {addr==0;}) ` — all 7 steps + inline constraints
  • uvm_create(req) ` — step 1 only (factory create)
  • uvm_send(req) ` — steps 2–7, skip randomization
  • uvm_rand_send(req) ` — steps 2–7 with randomization
  • uvm_rand_send_with(req, {constraints}) ` — steps 2–7 + constraints
  • uvm_do_on(seq, sequencer) ` — run sequence on specific sequencer (multichannel)

Explicit Flow (alternative to macros)

virtual task body();
  req = yapp_packet::type_id::create("req"); // no 'this' for data items
  start_item(req);                            // steps 2-3
  assert(req.randomize() with {addr == 0;});
  finish_item(req);                           // steps 5-7
endtask

Directed Stimulus with Create/Send

virtual task body();

  assert(req.randomize());   // randomize for legal packet
  req.addr = 3;              // overwrite specific field
  req.set_parity();          // housekeeping
  `uvm_send(req)             // send without re-randomizing

TLM (Transaction Level Modeling)

Concepts

  • Data flow: producer → consumer
  • Control flow: initiator requests, target responds
  • Put (push): producer is initiator → pushes data to consumer
  • Get (pull): consumer is initiator → pulls data from producer
  • Blocking (tasks): can suspend until complete; put(), get(), peek()
  • Non-blocking (functions): return 0/1 immediately; try_put(), try_get(), can_put(), can_get()

TLM Objects

  • port: in initiator component, provides access to implementation
  • imp: in target component, contains the implementation (requires all method variants)
  • export: for hierarchical routing of imp connections up the hierarchy

Uni-directional Connector Types

uvm_put_port/imp/export, uvm_get_port/imp/export, uvm_get_peek_port/imp/export, uvm_blocking_put_port/imp/export, uvm_nonblocking_put_port/imp/export

Connection Rule

connect() is called off the port (initiator), with target (imp/export) as argument.

Synchronous FIFO

The w_ptr and r_ptr and circulating with lower 3 bits the actual address inside the FIFO. 4th4^{th}4th﻿ bit is wrapper bit.

module syn_fifo #(parameter DEPTH = 8, WIDTH = 8)(
    input clk,
    input rstn,

    input [WIDTH-1:0] w_data,
    output reg full,
    input w_en,

    output reg [WIDTH-1:0] r_data,
    output reg empty,
    input r_en
);
    parameter ptr_depth = $clog2(DEPTH); // 3
    reg [ptr_depth:0] w_ptr, r_ptr; // 1+logN bits = 4bits
    reg [WIDTH-1:0] fifo [DEPTH-1:0]; 

    always_ff @(posedge clk or negedge rstn ) begin : write_side
        if (!rstn) begin
            w_ptr <= 0;
        end else (w_en && !full) begin
            w_ptr <= w_ptr + 1;
            fifo[w_ptr[0 +: ptr_depth]] <= w_data;
        end
    end

    always_ff @(posedge clk or negedge rstn ) begin : read_side
        if (!rstn) begin
            r_ptr <= 0;
            r_data <= 0;
        end else (r_en && !empty) begin
            r_ptr <= r_ptr + 1;
            r_data <= fifo[r_ptr[0 +: ptr_depth]];
        end
    end

    assign empty = (w_ptr == r_ptr);
    assign full = ((w_ptr[ptr_depth] != r_ptr[ptr_depth]) && (w_ptr[0 +: ptr_depth] == r_ptr[0 +: ptr_depth]));

endmodule

Asynchronous FIFO

module async_fifo #(
    parameter int DEPTH = 8,
    parameter int WIDTH = 8,
    localparam int ADDR_W = $clog2(DEPTH)
) (
    input  logic             clk_wr,
    input  logic             clk_rd,
    input  logic             rstn,

    input  logic [WIDTH-1:0] w_data,
    input  logic             w_en,
    output logic             full,

    output logic [WIDTH-1:0] r_data,
    input  logic             r_en,
    output logic             empty
);

    logic [WIDTH-1:0] mem [0:DEPTH-1];

    logic [ADDR_W:0] wptr_bin,  wptr_bin_n;
    logic [ADDR_W:0] wptr_gray, wptr_gray_n;
    logic [ADDR_W:0] rptr_bin,  rptr_bin_n;
    logic [ADDR_W:0] rptr_gray, rptr_gray_n;

    logic [ADDR_W:0] rptr_gray_wr_sync1, rptr_gray_wr_sync2;
    logic [ADDR_W:0] wptr_gray_rd_sync1, wptr_gray_rd_sync2;

    logic [ADDR_W:0] wq2_rptr_gray_inv2msb;

    function automatic logic [ADDR_W:0] bin2gray(input logic [ADDR_W:0] b);
        return (b >> 1) ^ b;
    endfunction

    always_comb begin
        wptr_bin_n  = wptr_bin;
        if (w_en && !full)
            wptr_bin_n = wptr_bin + 1'b1;
        wptr_gray_n = bin2gray(wptr_bin_n);
    end

    always_comb begin
        rptr_bin_n  = rptr_bin;
        if (r_en && !empty)
            rptr_bin_n = rptr_bin + 1'b1;
        rptr_gray_n = bin2gray(rptr_bin_n);
    end

    always_ff @(posedge clk_wr or negedge rstn) begin
        if (!rstn) begin
            wptr_bin  <= '0;
            wptr_gray <= '0;
        end else begin
            if (w_en && !full)
                mem[wptr_bin[ADDR_W-1:0]] <= w_data;
            wptr_bin  <= wptr_bin_n;
            wptr_gray <= wptr_gray_n;
        end
    end

    always_ff @(posedge clk_rd or negedge rstn) begin
        if (!rstn) begin
            rptr_bin  <= '0;
            rptr_gray <= '0;
            r_data    <= '0;
        end else begin
            if (r_en && !empty)
                r_data <= mem[rptr_bin[ADDR_W-1:0]];
            rptr_bin  <= rptr_bin_n;
            rptr_gray <= rptr_gray_n;
        end
    end

    always_ff @(posedge clk_wr or negedge rstn) begin
        if (!rstn) begin
            rptr_gray_wr_sync1 <= '0;
            rptr_gray_wr_sync2 <= '0;
        end else begin
            rptr_gray_wr_sync1 <= rptr_gray;
            rptr_gray_wr_sync2 <= rptr_gray_wr_sync1;
        end
    end

    always_ff @(posedge clk_rd or negedge rstn) begin
        if (!rstn) begin
            wptr_gray_rd_sync1 <= '0;
            wptr_gray_rd_sync2 <= '0;
        end else begin
            wptr_gray_rd_sync1 <= wptr_gray;
            wptr_gray_rd_sync2 <= wptr_gray_rd_sync1;
        end
    end

    assign empty = (rptr_gray_n == wptr_gray_rd_sync2);

    assign wq2_rptr_gray_inv2msb =
        {~rptr_gray_wr_sync2[ADDR_W:ADDR_W-1], rptr_gray_wr_sync2[ADDR_W-2:0]};

    assign full = (wptr_gray_n == wq2_rptr_gray_inv2msb);

endmodule

Register Renaming

Why Renaming? — False (Name) Dependencies

In a pipelined or out-of-order processor, data hazards between instructions can stall execution. There are three types:

HazardNameExampleFalse?RAWRead After WriteADD x1, x2, x3 then SUB x4, x1, x5❌ True dependency — cannot eliminate
WARWrite After ReadADD x4, x1, x2 then SUB x1, x3, x5✅ False — x1 in SUB is a different logical valueWAWWrite After WriteADD x1, x2, x3 then SUB x1, x4, x5✅ False — both write x1 but to independent values
WAR and WAW are name (false) dependencies — they only exist because two unrelated instructions use the same architectural register name. Register renaming eliminates them entirely by giving each write its own fresh physical register.

Key Hardware Structures

StructureRoleRename Map Table (RMT) / Register Alias Table (RAT)Maps each architectural register to its current physical register. Updated every rename cycle.
Free ListPool of unallocated physical registers. One is popped per destination register on rename; one is pushed back per commit (the stale register).Reorder Buffer (ROB)Tracks all in-flight instructions in program order for in-order commit. Stores (dest arch reg, new phys reg, stale phys reg) per instruction.

Rename Step-by-Step (per instruction)

  1. Read sources — look up each source arch reg in the RMT → get physical source registers
  1. Allocate destination — pop a free physical register from the Free List
  1. Record the stale register — the physical reg previously mapped to this arch dest (freed at commit)
  1. Update the RMT — write the new arch → physical mapping
  1. Enqueue into ROB — log source physicals, dest physical, and stale physical

Worked Example

Assume: RMT = {x1→p1, x2→p2}, Free List = [p3, p4, p5, ...]

// Instruction 1
ADD x1, x1, x1
  sources:  x1→p1, x1→p1
  allocate: p3 from free list
  renamed:  ADD p3, p1, p1
  stale:    p1  (old x1 mapping — freed at commit)
  RMT now:  {x1→p3, x2→p2}

// Instruction 2
SUB x2, x1, x2
  sources:  x1→p3, x2→p2   (reads updated RMT)
  allocate: p4 from free list
  renamed:  SUB p4, p3, p2
  stale:    p2
  RMT now:  {x1→p3, x2→p4}

// Instruction 3 — WAW hazard with Instr 1 is ELIMINATED
ADD x1, x2, x2
  sources:  x2→p4
  allocate: p5 from free list
  renamed:  ADD p5, p4, p4
  stale:    p3  (no dependency on Instr 1!)
  RMT now:  {x1→p5, x2→p4}

Instr 3 can execute independently of Instr 1 even though both write x1, because they now target distinct physical registers p3 and p5.

Commit and Free List Reclamation

Physical registers are freed only at commit, not at execution — this is critical for supporting rollback:

  • Instr 1 commits → p1 (stale) returned to Free List
  • Instr 2 commits → p2 (stale) returned
  • Instr 3 commits → p3 (stale) returned
Never free on execution — the stale register must survive in case the instruction is squashed before commit.

Rollback on Misprediction / Exception

All instructions younger than the faulting instruction are squashed:

  1. Restore the RMT — from a checkpoint saved at the branch (or by walking the ROB backwards)
  1. Return physical registers — all physicals allocated to squashed instructions go back to the Free List
  1. Flush the ROB — remove all entries younger than the faulting instruction

The visible architectural state after rollback must exactly match the state at the point of the branch/exception.

Verification Strategy

  • Golden reference model — software shadow of RMT and Free List stepping in lockstep with the DUT; compare after every rename cycle
  • Free List count invariant — |phys_regs| = |active RMT mappings| + |free list| + |stale pending commit| must hold at all times
  • Rollback self-check — after every squash, verify RMT matches the pre-branch checkpoint; verify Free List count increases by the correct amount
  • x0 property — assert x0's physical mapping never changes; x0 reads always return 0
  • Stall coverage — cover Free List empty and ROB full; verify all upstream stages stall with no side effects

module #(parameter N = 8) rr_abt(
  input clk, rstn,
  input  logic [N-1:0] req,
  output logic [N-1:0] gnt 
);

  // unmasked simple arbiter
  logic [N-1:0] unmasked_higher_pri_req;
  logic [N-1:0] unmasked_gnt;
  assign unmasked_higher_pri_req[0] = 0;
  assign unmasked_higher_pri_req[N-1:1] = unmasked_higher_pri_req[N-2:0] | req[N-2:0];
  assign unmasked_gnt = req & ~unmasked_higher_pri_req;

  // masked simple arbiter
  logic [N-1:0] masked_higher_pri_req;
  logic [N-1:0] masked_gnt;
  logic [N-1:0] masked_req;
  assign masked_req = req & ptr;
  assign masked_higher_pri_req[0] = 0;
  assign masked_higher_pri_req[N-1:1] = masked_higher_pri_req[N-2:0] | masked_req[N-2:0];
  assign masked_gnt = masked_req & ~masked_higher_pri_req;


  logic [N-1:0] ptr;

  always_ff @( posedge clk, negedge rstn ) begin
    if (!rstn) ptr <= {N{1'b1}};
    else begin
      if(|masked_req) ptr <= masked_higher_pri_req;
      else if (|req)  ptr <= unmasked_higher_pri_req;
    end
  end

Equivalence operators

  • == (equality): Returns true if operands are equal. If either operand contains x or z, the result is x (unknown).
  • ==? (wildcard equality): Treats z and ? in the right operand as "don't care" values. Allows pattern matching where certain bits can be ignored.
  • === (case equality): Returns true only if operands are identical, including x and z values. Always returns 0 or 1, never x. Used when you need to explicitly compare unknown or high-impedance values.
  • !=? (wildcard inequality): The inverse of ==?. Returns true if operands are not equal, treating z and ? in the right operand as "don't care" values.

  1. Argument passing by reference

    task automatic cpu_driver_ref(
	input logic [7:0] write_data,
	ref logic data_read,
	ref logic data_valid,
	ref logic [7:0] cpu_data);

	wait (data_read == 1);  // waits on real external signal

	data_valid = 0;         // external goes to 0

Cover Point

A user-defined item in a coverage model specifying an expression to cover and optionally a condition guarding its sampling.

Each coverpoint generates a series of counters (bins). By default there is a corresponding bin for each coverpoint.

Explicit Bins

illegal_bins take precedence, it overrides other bins.

c1: coverpoint var {bins V = {1,2,5};}

logic [3:0] var1;
ce: coverpoint var1 {

  // 1 bin for illegal values {0, 15}
  illegal_bins a = { 0, 15 };

  // 1 bin for ignored values {13, 14}
  // (value 15 is illegal)
  ignore_bins b = { [13:15] }

  // 1 bin for {2, 3}
  bins c = { 2, 3 };

  // 4 bins e[0], e[1], e[2], e[6]
  bins e[] = { [0:2], 2, 6 };

  // 2 bins - d[0] = {9,10,11,9}
  //        - d[1] = {12}
  bins d[2] = { [9:11], 9, [12:15] };

  // 1 bin for {4,5,7,8}
  bins f = default;

}
