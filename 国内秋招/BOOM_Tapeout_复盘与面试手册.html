0. 项目一句话 & 关键数字

一句话：用 Chipyard SoC Generator（Chisel/Scala 写的生成器框架）把 BOOM（Berkeley Out-of-Order Machine，RV64GC 乱序超标量核）以 MediumBoomConfig（2 发射、ROB 64）实例化成一个完整 SoC（BOOM tile + L1 I/D cache + TileLink 总线 + CLINT/PLIC/UART/BootROM/Debug）并 elaborate 成 Verilog，然后用 mflowgen 编排的 Cadence 商用流程（Genus 综合 → Conformal LEC → Innovus Stylus FlowKit 布局布线 → Tempus/Voltus 签核）打成 GDS，再用 Mentor Calibre 做 DRC/LVS；先在开源 freepdk-45nm（NangateOpenCellLibrary）上把流程跑通，再切换到 TSMC 工艺流片。

1,127,406标准单元实例（signoff 后 ChipTop）
46,912模块层级（flatten_effort=0，保留层级）
2,318,551nets（布线后恢复）
468,230时钟树 sink，41,377 个 clock gate

1. mflowgen 是怎么工作的（先理解框架，再理解流程）

mflowgen（Stanford Torng 组）是一个模块化、图（DAG）驱动的 ASIC 流程生成器。核心思想：每个 EDA 步骤是一个 node，节点之间用文件名连边；Python 里描述图，生成 Makefile；每个节点有 pytest 形式的前置/后置断言。

1.1 三个核心文件

文件作用BOOM 里的实例
construct.py用 Graph()/Node() 构建 DAG；connect_by_name(a,b) 按同名输出→输入自动连边；g.update_params() 把参数下发到所有节点designs/MediumBoom/construct-commercial-penn-stylus.py：design_name=ChipTop，clock_period=5.0，core_density_target=0.65，flatten_effort=0，FLOWTOOL_NUM_CPUS=16
configure.yml（每个节点）声明 inputs / outputs / commands / parameters / debug / preconditions / postconditions例：cadence-genus-synthesis 后置断言 'create_clock' in File('outputs/design.sdc')
.mflowgen.yml指向默认 construct 脚本construct: construct-commercial-penn-stylus.py

1.2 运行机制

# 在 build 目录里
mflowgen run --design ../designs/MediumBoom      # 生成 Makefile + .mflowgen/ 每步骤脚本
make status                                       # 看每一步状态
make 4            # 或 make cadence-genus-synthesis  —— 按编号/名字跑到某步
make clean-4      # 删掉该步骤目录（含 logs）
make debug-6      # 用 configure.yml 里的 debug 命令打开 GUI（如 flowtool -interactive）
mflowgen run --update                             # 修改 construct.py 后刷新 Makefile
mflowgen stash push/pull                          # 缓存耗时步骤的结果，跨 build 共享
  • 每个步骤目录形如 4-cadence-genus-synthesis/，里面 inputs/ 全是指向上游 outputs/ 的 符号链接（所以上游重跑会自动使下游失效，Make 依赖靠文件时间戳）。
  • mflowgen-check-preconditions.py / mflowgen-check-postconditions.py 是自动生成的 pytest：断言工具存在（Tool('genus')）、文件存在、日志里不含 Error :、SDC 里有 create_clock 等。这是流程级的"assertion"——和 UVM 里 checker 的思路完全一致。
  • ADK（ASIC Design Kit）抽象：adks/freepdk-45nm/pkgs/base/adk.tcl 定义 ADK_FILLER_CELLS / ADK_TIE_CELLS / ADK_WELL_TAP_CELL / ADK_ANTENNA_CELL / ADK_MAX_ROUTING_LAYER_INNOVUS / ADK_LVS_EXCLUDE_CELL_LIST / ADK_DRIVING_CELL 等变量，节点脚本只引用变量，不写死工艺名——换工艺（TSMC 28/40）只换 ADK。

2.0 Chipyard SoC Generator：从 Chisel 到一个 design.v

(a) Chipyard 是什么

Chipyard 是 Berkeley 的 SoC 生成器框架：它本身不是一颗芯片，而是一堆用 Chisel 写的"生成器"（Rocket、BOOM、Gemmini、Hwacha、外设 IP）和把它们拼成 SoC 的胶水——Rocket Chip 的 Diplomacy（参数协商）和 TileLink（片上互连协议）。一颗 SoC 由一个 Scala Config 描述，Config 由若干 fragment 叠加而成：

// generators/chipyard/src/main/scala/config/BoomConfigs.scala
class MediumBoomConfig extends Config(
  new boom.common.WithNMediumBooms(1) ++      // 1 个 MediumBoom tile（fetch 4 / decode 2 / ROB 64）
  new chipyard.config.AbstractConfig)         // 总线拓扑 + BootROM + CLINT + PLIC + UART + Debug + 串行 TL 接口
// AbstractConfig 里再叠：WithDefaultMemPort / WithSerialTLMem / WithUART / WithNoDebug ... 每个 fragment 只改 Parameters 的一个 key
  • Diplomacy：TileLink 的位宽、地址空间、source/sink ID 数量不是手写的，而是各节点在 elaboration 之前两轮协商出来的——这就是为什么改一个 fragment（比如把 L1 D-cache 改成 8 路）整个 SoC 的总线会自动适配。
  • ChipTop / TestHarness：ChipTop 是真正流片的顶层（System + IO cell/clock 的 IOBinder），TestHarness 在它外面挂仿真模型（DRAM 模型、串口、tohost）。后端只吃 ChipTop，所以约束里的时钟端口是 clock_uncore（由 WithClockGroups/HarnessClockInstantiator 生成）。

(b) Chisel 与 elaboration 流水线

Chisel 是嵌在 Scala 里的硬件构造语言：写的是"生成硬件的程序"，运行这段程序（elaboration）得到 FIRRTL 中间表示，再经 FIRRTL/CIRCT（firtool）的一系列 transform 变成 Verilog：

阶段发生什么对后端/验证的影响
Scala 运行按 Config 递归构造 Module 树，Diplomacy 两轮协商参数参数错误在这一步就报（Scala 异常），不会生成 RTL
CHIRRTL → FIRRTL推断位宽、展开 when、把 Mem/SyncReadMem 变成 FIRRTL memory位宽推断出来的名字/宽度和你脑子里的可能不一样，看生成的 .fir
FIRRTL transformsDedup（相同模块去重）、常量传播、DCE、ReplSeqMem（把时序存储器抽成黑盒 + .mems.conf）、InferReadWrite、dontTouch 保护Dedup 让 BOOM 的多个相同 issue slot 共用一个模块定义（综合前 46,912 个模块实例，定义少得多）；ReplSeqMem 决定哪些数组能换成 SRAM 宏
Verilog emit输出 *.top.v（ChipTop 及其下所有模块）、*.top.mems.v（被抽出的存储器的行为实现）、*.harness.v、*.top.f 文件列表、*.plusArgs名字是自动生成的（_T_123、_GEN_45、io_deq_bits_uop_br_mask），调试要靠 Chisel 里 suggestName/dontTouch
# 在 acghaswell16 上
./build-setup.sh --skip-firesim --skip-marshal              # conda + 子模块，约 2 小时
cd sims/verilator
make CONFIG=MediumBoomConfig                                  # elaborate + Verilator 编译（BOOM 比 Rocket 慢 3-4 倍）
make CONFIG=MediumBoomConfig run-asm-tests -j16              # riscv-tests：rv64ui/um/ua/uf/ud/mi/si + 乱序核特有的 rv64 ma/mi 场景
make CONFIG=MediumBoomConfig run-bmark-tests                 # dhrystone / median / qsort / towers 等，顺便看 IPC

# 聚合成后端要的单文件
cd generated-src/chipyard.harness.TestHarness.MediumBoomConfig/gen-collateral
echo `pwd`/chipyard.harness.TestHarness.MediumBoomConfig.top.mems.v >> ../chipyard.harness.TestHarness.MediumBoomConfig.top.f
python3 cat-files.py ../chipyard.harness.TestHarness.MediumBoomConfig.top.f > design.v
  • make run-asm-tests 是流片前最基本的 RTL 功能验证（ISA 级 self-checking test，写 tohost 判 pass）；BOOM 还会额外跑 rv64mi-p-*（异常/特权级）和乱序相关的 fence/amo 用例，因为 LSQ 的 memory disambiguation 是最容易出功能 bug 的地方。
  • 后端只吃一个文件，所以用 cat-files.py 把 *.top.f 列表里的所有 .v/.sv 拼接，并且手动把 *.top.mems.v（ReplSeqMem 抽出的存储器：BTB/TAGE 表、L1 tag/data 阵列、BOOM 的 FTQ 等的行为实现）追加进列表——漏掉它 Genus 报 Cannot resolve reference（后置断言会抓住）。
  • gen-collateral 里还有几个"仿真专用"的文件必须一起带上：plusarg_reader.v（+plusarg 读取，`ifdef SYNTHESIS 下退化为常量）、EICG_wrapper.v（Chipyard 的行为级 ICG 时钟门控黑盒）、ClockDividerN.sv/ClockSourceAtFreq 等时钟黑盒——这些是 BOOM 项目里综合阶段 unresolved reference 的第二大来源（见 Bug #27–#29）。
  • 生成的 design.v 有上百 MB，不进版本库（TinyRocket 打样阶段就把 rtl/outputs/design.v 从 git 删了，commit 37252c4），各人自己生成。

(c) MediumBoom 微架构（后端/验证都要能说出来）

参数（MediumBoomConfig 默认）值为什么后端/验证关心
Fetch / Decode 宽度4 条/拍 fetch（fetch buffer 16 项，FTQ 32）/ 2 条/拍 decode-rename-dispatch-commit前端 F0–F3 四级 + TAGE-L/BTB/RAS 预测器的表是 mems.v 里最大的存储器之一
ROB64 项（32 行 × 2 列）commit/异常/误预测回滚都在这里，是 trace-compare 的比对点
物理寄存器堆80 int / 64 fp（rename map + free list + busy table）多读多写端口的触发器阵列，面积和 hold 修复的大头（Bug #30）
Issue queuemem 12 / int 20 / fp 16（分布式，年龄矩阵仲裁）CAM 唤醒逻辑 = 综合最长路径的主要候选
LSQLDQ 16 / STQ 16，load 推测 + 地址冲突检测重放功能 bug 高发区；验证要覆盖 store-load forward、ordering failure、fence
分支maxBrCount 12（分支掩码位宽 12），brupdate 广播 kill分支掩码 fanout 到所有 IQ/ROB/LSQ 项，CTS/布线拥塞热点；你的 UVM 环境检查的就是"被 kill 的 uop 不得写回"
执行单元2 个 int ALU（其中一个含 iMul/iDiv、CSR、分支单元）、1 个 mem 单元、FPU + FDiv/FSqrt（非流水）ALU 延迟对齐到 FPU 以共享写回口——你 UVM 环境里"所有流水单元共享一个延迟"的假设来自这里
L1I$ 16 KB 4 路；非阻塞 D$ 16 KB 4 路，2 个 MSHRtag/data 阵列是 SRAM 宏候选；miss-under-miss 是覆盖点

流水线：Fetch(F0–F3) → Decode → Rename → Dispatch → Issue → Register Read → Execute → Memory → Writeback → Commit。和 Rocket 的 5 级顺序流水相比，多出的 Rename/Issue/ROB/LSQ 全是控制密集、CAM 密集的结构，这解释了为什么同一条流程在 BOOM 上综合时间、CTS sink 数、hold 修复量都翻了几倍。

2.1 ADK 与约束（SDC）

# designs/MediumBoom/constraints/constraints.tcl（核心部分，clock_period=5.0）
set clock_net  clock_uncore              ;# Chipyard 顶层时钟端口名
set clock_name chip_clock_uncore
create_clock -name ${clock_name} -period ${clock_period} [get_ports ${clock_net}]
set_load -pin_load $ADK_TYPICAL_ON_CHIP_LOAD [all_outputs]        ;# 7 (pF 单位按 lib)
set_driving_cell -no_design_rule -lib_cell $ADK_DRIVING_CELL [all_inputs]   ;# INV_X2
set_input_delay  -clock ${clock_name} [expr ${clock_period}/2.0] [all_inputs]  ;# 非零，避免输入寄存路径插 hold buffer
set_output_delay -clock ${clock_name} 0 [all_outputs]
set_max_fanout 20 $design_name
set_max_transition [expr 0.25*${clock_period}] $design_name

要点：时钟必须用 create_clock 定义在主时钟端口上；create_generated_clock 只能挂在已有 master clock 的下游（PLL 输出、分频器输出），源=目标的写法会被 Genus 静默丢弃（见 Bug #1）。

2.3 Conformal LEC（cadence-conformal-lec，2026-06 新增）

  • 先用 Genus 恢复 design_for_lec.checkpoint，用 write_do_lec 自动生成两份 dofile：rtl2gate（golden=RTL，revised=fv_map 中间映射网表）和 gate2gate（golden=fv_map，revised=最终优化网表）。
  • 两段式的原因：Genus 在 syn_opt 里会做时序驱动重构、寄存器合并、时钟门控插入，直接 RTL vs 最终网表容易出现大量 non-equivalent/abort 点；用 fv/ 目录里的 mapping 信息（寄存器名映射、常量寄存器、合并信息）分段验证成功率高得多。
  • 后置断言：两份 log 都含 PASS。
  • 连线：rtl.o('design.v') → lec.i('design.ref.v')，synth.o('design.v') → lec.i('design.impl.v')——这是 mflowgen 里少见的按端口名显式连边而不是 connect_by_name。

5. 经验总结（可直接讲给面试官）

流程即代码 + 断言
mflowgen 把每个 EDA 步骤的输入/输出/前后置条件写成可执行的 pytest；我把这种"每一步都能被自动检查"的思路带到验证：checker、scoreboard、覆盖率门槛都是"后置断言"。
配置单一真源
工艺相关的一切只在 adk.tcl 定义；setup.yaml 从它生成而不是手写；硬编码路径是多人协作的第一大坑。
缩短迭代回路
PnR 6 小时的项目里，能否 80 秒复现一个 bug 决定了一周能修几个问题；对应到 DV 就是：小 case 复现、保存 seed、单测直接 run 到失败点。
工具版本是变量
Innovus 23 删 postroute 步骤、legacy→CUI 命令翻译、参数改名——升级前先跑 smoke flow。
物理与逻辑的边界
LVS 网表要排除 filler/welltap；GDS 要 merge 标准单元；antenna 只能布线后修；rail analysis 依赖 QRC 数据——理解"为什么"比背命令重要。
签核是一组独立视角
LEC（功能等价）、STA（时序）、IR（电源）、DRC（可制造）、LVS（版图=网表）、GLS（带 SDF 的门级仿真）各自证明一件事，缺一个就不能 tapeout。

A. 项目深挖：面试官会顺着你的简历问

介绍一下这个 tapeout 项目的整体流程，每一步的输入输出是什么？

Chipyard SoC Generator 按 MediumBoomConfig（Scala Config = BOOM tile fragment + AbstractConfig 的总线/外设 fragment）elaborate：Chisel → FIRRTL（Dedup、ReplSeqMem 抽存储器）→ Verilog，得到 ChipTop 的 *.top.v + *.top.mems.v，聚合成一个 design.v；配合 SDC（create_clock 5 ns、IO 延迟、驱动/负载、max fanout/transition）和 ADK（lib/lef/captable/adk.tcl）进入 Genus 综合，产出门级网表、SDC、SDF、SPEF、LEC checkpoint；Conformal 做 RTL→中间网表→最终网表两段等价检查；Innovus Stylus FlowKit 按 floorplan→place→cts→postcts→route→postroute→signoff 执行，signoff 产出 GDS、LVS 网表、带 PG 的仿真网表、SDF、SPEF，并调 Tempus 做多角 STA、Voltus 做功耗；最后 Calibre 把标准单元 GDS 合并后做 DRC 和 LVS。整个 DAG 由 mflowgen 编排，每步有前后置断言。

延伸：为什么综合要读 LEF（物理感知综合，估算线长/拥塞）？SPEF 综合阶段为什么就有（Genus 基于 captable 的预估寄生，用于 syn_opt）？SDC 在综合前后为什么会变（工具会把 set_max_transition 等 DRC 约束、生成的时钟门控写回）？
Chipyard SoC Generator 和 Chisel 是怎么工作的？你为什么用生成器而不是手写 Verilog？

Chisel 是嵌在 Scala 里的硬件构造语言：代码是"生成硬件的程序"，运行它（elaboration）产生 FIRRTL IR，再由 FIRRTL/CIRCT 做 Dedup、常量传播、存储器抽取（ReplSeqMem）后 emit Verilog。Chipyard 在其上提供 SoC 级的生成器框架：核（Rocket/BOOM）、加速器、外设都是参数化生成器，靠 Diplomacy 协商 TileLink 的位宽/地址/ID，用 Scala Config 的 fragment 叠加描述整颗 SoC（MediumBoomConfig = WithNMediumBooms(1) ++ AbstractConfig）。好处：改一个参数（cache 路数、ROB 深度、加一个加速器）整颗 SoC 自动一致；代价：生成的 Verilog 名字难读、仿真专用黑盒（plusarg_reader、EICG_wrapper）和寄存器数组式存储器（mems.v）在后端要额外处理。

延伸：Diplomacy 的两轮协商解决什么问题（参数在图上双向传播后再 elaborate）；dontTouch/suggestName 对调试和 LEC 的作用；FIRRTL Dedup 对 uniquify/LVS 的影响；Chisel 的 assert/printf 在综合下如何被 `ifndef SYNTHESIS 去掉。
Chipyard 生成的 RTL 拿去综合有哪些"坑"？你怎么处理的？

四类：（1）*.top.mems.v 是存储器的寄存器数组实现，Genus 会把 TAGE/BTB/L1 阵列综合成触发器 + mux 树，综合时间和面积爆炸——freepdk 没有 SRAM compiler，我们缩小预测器/cache 配置并让 Genus 走 memory 推断，TSMC 上则按 .mems.conf 换 SRAM 宏；（2）仿真黑盒 plusarg_reader / ClockDividerN / EICG_wrapper 不在默认文件列表里，导致 Cannot resolve reference，加进 .f 并用 read_hdl -define SYNTHESIS；（3）EICG_wrapper 是 latch 型 ICG 的行为实现，要 dont_touch 或映射到工艺 ICG 单元，否则 latch 警告与 LEC 问题；（4）自动生成的名字 + FIRRTL Dedup + Genus update_names -prefix 三重改名让 LEC 与 LVS 的名字映射变复杂，用 Genus 的 fv/ name map。

延伸：为什么存储器是"生成器和工艺之间的接口"；OpenRAM 与商用 SRAM compiler 的差别；把行为级 SRAM 换成宏之后验证怎么保证一致（黑盒 LEC + 定向读写 + GLS）。
为什么要做两段 LEC（rtl2gate 和 gate2gate），而不是直接 RTL 对最终网表？

综合优化（时序驱动重构、寄存器常量/等价合并、时钟门控插入、寄存器复制、重定时）会让最终网表和 RTL 的比较点（key points：寄存器、端口、黑盒引脚）对应关系变复杂，直接比对容易出现大量 unmapped/abort。Genus 在映射阶段（fv_map）保存中间网表和 fv/ 目录里的变换信息（寄存器合并、常量寄存器、名字映射）；RTL vs fv_map 主要是"逻辑映射正确"，fv_map vs 最终网表主要是"优化没改功能"，每段的 mapping 都简单，Conformal 能自动消化这些 guide 信息。

延伸：LEC 的 non-equivalent 常见原因（未初始化寄存器、X 的处理差异、时钟门控使能极性、常量传播、黑盒）；LEC 和仿真的关系（LEC 只证明结构等价，不证明 RTL 正确）；后布局 LEC（signoff 网表含 buffer、ECO 后）用什么做 golden。
你提到 create_clock 的断言失败，具体是怎么回事？create_clock 和 create_generated_clock 的区别？

约束里把主时钟端口 clock_uncore 用 create_generated_clock -source [get_ports clock_uncore] -divide_by 1 [get_ports clock_uncore] 定义，源和目标是同一个端口，而且端口上游没有任何 master clock，Genus 认为它是退化定义直接丢弃，输出 SDC 里没有时钟，所以 mflowgen 的后置断言 'create_clock' in design.sdc 失败。修法是改回 create_clock。区别：create_clock 定义主时钟（端口或 pin，独立源）；create_generated_clock 定义派生时钟，必须指向已有 master，用于分频器输出、PLL 输出、时钟 mux 输出，它继承 master 的相位关系，让 STA 能算跨这两个时钟的路径。

DRC 报了 124 条，怎么分类和处理？antenna 违例是什么？

先按 rule 聚类：60 条 antenna（metal3–6）、63 条 Metal8.7、1 条 Metal9.6。Antenna 效应：制造过程中（金属刻蚀/CMP）长金属线像天线一样收集等离子体电荷，如果这根线只连着 MOS 栅极而没有通路放电，电荷会击穿栅氧。修法是插反偏二极管（ANTENNA_X1）给电荷放电，或者"跳层"（把长线先打到高层再下来，减小单层面积比）。在 SFK 里加了 fix_antennas 步骤（route_detail_fix_antenna + route_antenna_diode_insertion）。Metal8.7/9.6 是电源网格所在的 M8/M9 层的间距/密度规则，说明 power strategy 里 stripe 的宽度/间距要按 freepdk 规则调。

LVS 里为什么要排除 filler / welltap？LVS 的输入到底是什么？

LVS 比较"版图提取的网表"和"逻辑网表（schematic）"。Filler、welltap、endcap 是纯物理单元：没有逻辑功能，在综合网表里不存在，但在版图里有（它们只连电源/衬底）。如果 Innovus 写出的 LVS 网表里包含它们，而 CDL 侧只有它们的电源连接，会造成实例数不匹配；所以 design.lvs.v 用 ADK_LVS_EXCLUDE_CELL_LIST = FILL* WELLTAP* 过滤，同时 Calibre 规则文件把这些单元当作可忽略。输入：合并了标准单元 GDS 的 design_merged.gds、design.lvs.v、标准单元的 .cdl/.spi、LVS 规则文件。

延伸：hcells 是什么（层次化 LVS 对应关系）；LVS 里的 "INCORRECT" 与 "CORRECT" 判定；为什么 GDS 需要先 merge（Innovus GDS 只含单元引用）。
MMMC 是什么？你们 wc 视图为什么说"极悲观"？

Multi-Mode Multi-Corner：模式（功能/测试/低功耗，对应不同 SDC）× 角（工艺 P、电压 V、温度 T + RC 提取角）。一个 analysis view = constraint_mode + delay_corner；delay_corner 又分 early（用于 hold 的最快路径）和 late（用于 setup 的最慢路径）。项目里 delay_wc 用 bc 库做 early、wc 库做 late，也就是同一个视图里 launch 用最慢、capture 用最快（setup）或反过来（hold），比真实芯片同一时刻同一角要悲观，等于用一个视图覆盖了 setup 和 hold 的最坏情况，代价是过度设计。

延伸：OCV/AOCV/POCV 的区别；为什么 hold 用 bc 角还要在 wc 角再看一次（温度反转，40nm 以下低温未必最快）；CTS 为什么选 cts_primary_delay_corner delay_wc。
PnR 各阶段（floorplan/place/CTS/route）验证工程师需要关心什么？

Floorplan：pin 位置、宏位置决定后续时序，验证不直接参与但要提供 IO 约束合理性；Place/预 CTS 优化后：网表变了（buffer、重复寄存器）但功能不变，LEC 验证；CTS 后：时钟树真实，hold 修复插 buffer，需要带 SDF 的 GLS 抓复位释放、异步复位去断言、时钟门控的 glitch；Route 后：SPEF 真实，STA signoff；功耗分析需要验证给 SAIF/VCD（真实翻转率）。此外 DFT（scan）插入后 scan shift/capture 模式需要 GLS。

延伸：零延迟 GLS 与带 SDF GLS 各抓什么 bug；X-pessimism 怎么处理（+nospecify、初始化、$deposit、X-prop 工具）；GLS 时序违例（timing check）和功能失败怎么区分。
mflowgen 的 pre/postconditions 的设计给你什么启发？

把"步骤成功"定义成可执行断言而不是人眼看日志：工具存在、输入文件存在、日志无 Error :、SDC 含时钟、LEC log 含 PASS、LVS report 无 INCORRECT。每条断言都对应一个曾经踩过的坑。对验证来说就是：每个 test 有 end-of-test checker（队列清空、objection 归零、错误计数 0、覆盖率阈值），回归结果由脚本判定不是人判定。

延伸：你会给 UVM 回归加哪些"后置断言"？（无 UVM_ERROR、scoreboard 期望队列为空、所有 sequence 正常结束、覆盖率增量非负、仿真时间未超时）
BOOM 的 RTL 是怎么验证的？如果让你给它搭 UVM 环境怎么做？

项目里用 Verilator 跑 riscv-tests（ISA 级 self-checking 汇编，写 tohost 判 pass）和 Chipyard 自带 benchmark（顺便看 IPC 是否符合 MediumBoom 预期）；BOOM 自带的 chisel3.assert（如 ROB/LSQ 一致性断言）在仿真里以 $fatal 生效。给 BOOM 搭 UVM 我会分层：（1）core 级：以指令流为激励，用 ISS（Spike）做参考模型，通过 trace 接口（commit log：PC、指令、寄存器写、CSR 写、异常）逐条比对——即 co-simulation/trace-compare；随机指令生成用 riscv-dv；（2）存储子系统：TileLink/AXI agent 打 cache，scoreboard 用一个行为级内存模型；（3）系统级：passive agent + 软件测试 + 覆盖率（指令类型、异常/中断、特权级切换、cache miss/hit、分支预测命中、LSQ 的 store-load forwarding 与 ordering failure 重放）。乱序核的关键是按 commit 序比对（ROB 提交口），而不是按执行序。

延伸：trace-compare 遇到乱序核（BOOM）怎么办（按 commit 顺序比对）；中断/异步事件怎么和 ISS 对齐（tandem 模式注入）；riscv-dv 的覆盖模型；riscv-arch-test 合规套件。

B. UVM 与验证方法学

描述一个完整的 UVM 环境结构，以及每个组件的职责。

test（配置 + 启动 sequence）→ env（例化 agent、scoreboard、coverage、RAL，负责 TLM 连线）→ agent（sequencer：仲裁 sequence 到 driver；driver：把 transaction 转成引脚时序；monitor：从引脚重建 transaction 并 broadcast）→ interface（信号、clocking block、SVA）。sequence_item 是数据，sequence 是激励意图，config object 是旋钮，config_db 传递 vif/cfg，factory 提供替换。参考模型在 scoreboard 里，独立于 RTL 实现。

延伸：为什么 monitor 不能复用 driver 采的数据（passive 模式、真实观测）；agent 什么时候设为 passive；一个 env 里多个相同 agent 怎么区分（实例名、cfg 数组、uvm_analysis_imp_decl）。
UVM phase 有哪些？为什么 build 是自顶向下、connect 是自底向上？run_phase 与 main_phase 的关系？

build → connect → end_of_elaboration → start_of_simulation → run（并行 12 个子 phase：pre_reset/reset/post_reset/pre_configure/configure/post_configure/pre_main/main/post_main/pre_shutdown/shutdown/post_shutdown）→ extract → check → report → final。build 自顶向下是因为父组件必须先创建子组件（create 在父的 build 里）；connect 自底向上是因为子组件的端口要先存在，父才能连。run_phase 与 12 个子 phase 并行执行，一般只用 run_phase 或只用子 phase，混用要小心 objection。

延伸：phase jump（phase.jump(uvm_reset_phase::get())）用于运行中复位；set_drain_time；phase_ready_to_end 钩子；为什么 final_phase 是 function。
objection 机制怎么工作？测试结束不了/提前结束了怎么排查？

run-time phase 在所有 objection 被 drop 且 drain time 过后结束。通常在 test 的 run_phase raise，sequence 结束后 drop；也可在 sequence 的 pre_body/post_body 里 raise/drop（用 starting_phase）。结束不了：某处 raise 未 drop（+UVM_OBJECTION_TRACE 查看）、driver 等 ready 死等、sequence 卡在 get_response；提前结束：忘记 raise、在错误的 phase 里 raise、driver 还没把最后一笔打完就 drop（用 drain time 或让 driver 在 item_done 前完成）。

延伸：uvm_top.set_timeout；为什么不建议在 driver/monitor 里 raise objection；phase.raise_objection(this, "desc", count) 的 count。
sequence 和 driver 之间的握手：get_next_item/item_done、get/put、try_next_item 有什么区别？response 怎么回？

get_next_item 阻塞取 item，driver 必须调 item_done() 才能取下一个（sequence 的 finish_item 在 item_done 后返回）；get 相当于 get_next_item+item_done 一起做，sequence 立刻返回，适合流水线 driver；try_next_item 非阻塞，没 item 时返回 null，用于需要每拍驱动 idle 的协议；peek 看不取。Response：driver seq_item_port.put_response(rsp) 或 item_done(rsp)，sequence 用 get_response(rsp)；需要 rsp.set_id_info(req)，否则 sequence 收不到；不取 response 会导致 response queue 溢出报错（可 use_response_handler）。

延伸：pipelined driver（同时处理多笔 outstanding）怎么写（fork + 队列 + get）；sequencer 的仲裁模式（FIFO、随机、优先级、lock/grab）；`uvm_do_with 展开后是什么。
config_db 和 resource_db 的区别？config_db 常见坑？

config_db 是 resource_db 的类型化、带层次作用域的封装：set(cntxt, inst_name, field, value) 用 cntxt 的完整路径 + inst_name 作为 glob 键；get 时按调用者路径匹配，层次越高的 set 优先级越高，同层后 set 覆盖先 set。坑：类型参数不一致（virtual dut_if 与 virtual dut_if.mp）导致 get 失败；在 build_phase 之后 set 子组件已 build 完拿不到；通配符写错；字符串拼错难以发现（用 +UVM_CONFIG_DB_TRACE）；性能问题（大量 get，改用 cfg 对象一次传）。

延伸：uvm_config_db::wait_modified；set_config_int 老接口；为什么推荐把所有旋钮放一个 cfg 对象。
factory override 的用法和限制？type override 和 instance override 优先级？

set_type_override_by_type(orig::get_type(), new::get_type()) 全局替换；set_inst_override_by_type(orig, new, "path") 按实例路径替换；instance override 优先于 type override；新类型必须是原类型的子类（多态），且组件用 type_id::create 创建（用 new 就无效）。用途：错误注入 driver、corner sequence、换参考模型。限制：参数化类 override 要精确匹配参数；override 必须在 create 之前（通常在 test 的 build_phase 最前面）。

延伸：uvm_factory::print() 调试；`uvm_object_utils 里注册了什么；sequence 的 override 怎么做（同样走 factory）。
Scoreboard 怎么设计？顺序/乱序、多入口、如何处理丢包与超时？

核心是"期望流"与"实际流"的匹配策略：顺序协议用队列 pop_front；乱序（AXI 多 ID、乱序核 writeback）用关联数组按 ID/tag 索引，同 ID 内保序；多入口用 uvm_analysis_imp_decl 或 uvm_tlm_analysis_fifo；比对用 !==（抓 X），复杂数据用 do_compare；丢包用 check_phase 检查剩余；超时用每笔事务带时间戳，watchdog 进程扫描超过阈值的未匹配项报错；参考模型独立实现（不抄 RTL），复杂算法 DPI-C。你的 BOOM 环境额外检查"被 kill 的 uop 不得写回"。

延伸：predictor 型（先算期望）vs comparator 型（两路都采）；cycle-accurate 与 transaction-accurate 参考模型的取舍；scoreboard 里能不能用 #delay（不应该，只依赖事务）。
RAL（寄存器模型）的组成？frontdoor/backdoor 区别？mirror/predict/explicit predictor 是什么？

uvm_reg_field → uvm_reg → uvm_reg_block → uvm_reg_map（地址映射 + sequencer + adapter）。frontdoor 走总线（driver 打事务），backdoor 用 uvm_hdl_read/deposit 直接访问 RTL 变量（需要 hdl_path），零时间。mirror 是模型里对 RTL 值的镜像，desired 是期望写入值；write/read 后自动 predict 更新 mirror（auto predict），更严格的做法是 explicit predictor 监听 monitor 的 analysis port 更新 mirror（能看到非 RAL 发起的访问）。mirror(UVM_CHECK) 读回并与镜像比对。字段访问类型（RW/RO/W1C/WARL 等）和 volatile 决定 predict 行为。

延伸：内建 sequence（uvm_reg_hw_reset_seq、bit_bash_seq）；WARL 字段怎么建模；CSR 有副作用（如 fflags 由 FP 指令累积）怎么让 mirror 正确（volatile + 显式 predictor）；RAL 从 IP-XACT/CSV 自动生成。
功能覆盖率和代码覆盖率各自的局限？覆盖率收敛不上去怎么办？

代码覆盖（line/branch/toggle/FSM/condition）由工具自动收集，说明"RTL 被执行过"但不说明"功能被检查过"，也不能反映验证计划意图；功能覆盖由人定义 covergroup/断言覆盖，反映意图但容易漏定义。收敛：先分析未覆盖项分类——不可达（写 waiver/exclusion，附理由）、随机分布偏置不够（改约束权重、定向 sequence）、测试不足（新 test）、covergroup 定义错（bins 不合理）；用 ranked 报告找贡献最大的 test；用 seed 数量与覆盖率曲线判断是否饱和。

延伸：cross 的 ignore_bins/illegal_bins；sample() 何时调用（事务完成时，不是每拍）；覆盖率合并（urg/imc/vcover merge）；assertion coverage。
怎么从 spec 提取测试点、制定验证方案？

按特性拆：接口（每个端口的协议合法/非法场景）→ 功能（每条 spec 语句变成可检查的陈述）→ 配置/模式（寄存器组合）→ 边界（FIFO 满空、计数器溢出、地址边界、复位中途）→ 异常/错误注入 → 性能（吞吐、延迟）→ 并发/竞争。每个测试点写明：激励、检查方式（SB/SVA/end-of-test）、覆盖点、优先级、状态。验证方案还包括环境架构图、参考模型策略、回归策略、退出标准（覆盖率阈值、bug rate 曲线、所有 P0 测试通过）。

延伸：怎么评估 spec 的模糊点（写 issue 问设计）；模块级和系统级测试点怎么划分（系统级只测集成、跨模块交互、软件流程）；验证报告包含什么。
virtual sequence / virtual sequencer 是什么，什么时候用？

当一个场景需要多个 agent 协同（如 AXI 主写 + 中断 + 寄存器配置），virtual sequencer 只是持有各个真实 sequencer 句柄的容器（不产生 item），virtual sequence 在其上 start，内部 fork 各子 sequence 到对应 sequencer。它把"场景编排"从 test 移到可复用的 sequence，test 只挑 virtual sequence。也可以不用 virtual sequencer，直接在 sequence 里通过 p_sequencer/env 句柄拿 sequencer。

延伸：`uvm_declare_p_sequencer；sequence 里怎么等一个事件（uvm_event pool）；多 agent 同步用 barrier。
UVM 里 uvm_component 和 uvm_object 的区别？为什么 transaction 是 object 而 driver 是 component？

component 有层次（parent）、有 phase、静态存在于整个仿真、可被 config_db 按路径定位；object 无层次、无 phase、动态创建销毁、可 copy/compare/pack、可作为数据流动。transaction 需要被复制、比较、通过 TLM 传递，所以是 object；driver 需要参与 phase 并固定挂在层次树上，所以是 component。sequence 也是 object（动态、可嵌套、可 factory）。

延伸：为什么 uvm_sequence 不能用 config_db 按 this get（它不是 component，要用 m_sequencer 或 null 作 context）；field automation 宏的性能代价。
TLM：analysis port 与 blocking put/get port 的区别？TLM FIFO 用在哪？

analysis port 是 1 对 N 广播、非阻塞、函数调用（write），发送者不关心是否有订阅者（可 0 个）；put/get port 是 1 对 1、可阻塞、任务调用，有握手语义。uvm_tlm_analysis_fifo 把 analysis 广播缓冲成可以阻塞 get 的队列，scoreboard 用两个 fifo 分别接期望和实际，在 run_phase 里 fork 两路 get 后比对，避免 imp 里写复杂逻辑。

延伸：TLM 2.0（generic payload、b_transport/nb_transport）用于 SystemC 联合仿真；port/export/imp 三者角色；write 里为什么要 clone 事务（monitor 复用同一对象会被后写覆盖）。
随机激励怎么"有效"？约束求解慢或失败怎么办？

有效 = 覆盖驱动 + 分层约束：base 约束保证合法，test 通过 constraint_mode/继承添加偏置（dist、权重）、solve...before 控制分布、randcase 挑场景。求解失败：rand_mode 查看冲突约束、简化关系、避免非线性/除法/大数组约束、把复杂关系用 post_randomize 计算；慢：减少 rand 变量、缩小范围、避免动态数组 size 和内容一起约束、用 std::randomize() 局部随机。

延伸：pre_randomize/post_randomize；randc 的限制；seed 管理与可复现（打印 seed、命令行传 seed）；软约束 soft 的优先级。
模块级环境怎么复用到系统级？

接口 agent 设 passive（driver 不例化，monitor 保留），继续做协议检查和覆盖；scoreboard 换成系统级数据流检查（端到端）；模块级 sequence 变成 virtual sequence 的子步骤（如果该接口在系统级仍是外部端口则保持 active）；RAL 合并成系统级 reg block（add_submap）；SVA 用 bind 绑到内部实例；配置对象通过顶层 cfg 分发。关键是模块级不写任何层次引用，所有依赖走 cfg/vif。

延伸：系统级用 C 测试（processor-driven）配合 UVM（软硬协同，DPI/后门同步）；仿真速度问题（emulation/FPGA）；系统级不该重复模块级覆盖。
你的 BOOM 执行流水线 UVM 环境里最难的部分是什么？

三点：（1）IEEE-754 特殊操作数（±0、±inf、qNaN/sNaN、subnormal 极值）的交叉与 bit-exact 比对，包括 canonical NaN 和 NV/DZ/OF/UF 标志，参考模型自己实现而不是抄 RTL；（2）CSR 用 RAL 建模：CSR 指令是串行化的，adapter 把 RAL 读写映射成 CSRRW/CSRRS uop，driver 等到写回返回旧值才完成，这样 RAL read 拿到的是真实 DUT 数据；WARL、只读 ID 寄存器、volatile 计数器、fflags 副作用都要按字段属性建模；（3）分支误预测 kill：uop 携带 branch mask，广播 brupdate 后 scoreboard 必须确认被 kill 的 uop 没有写回。此外 iDiv/FDiv 非流水的反压在 driver 里要正确处理。

延伸：如果接真实 BOOM RTL 怎么做（Chipyard 生成 MediumBoomConfig，bind interface 到 execution unit，softfloat DPI 做 FP 参考）；多发射怎么扩展（每个 issue port 一个 agent）。

C. SystemVerilog 语言

logic / wire / reg 的区别；always_ff / always_comb / always_latch 为什么比 always 好？

logic 是四态类型，可被单个 always/assign 或一个 continuous driver 驱动，不能多驱动（多驱动要用 wire）；reg 只是 Verilog 遗留名，不代表寄存器。always_ff 要求综合成时序逻辑且敏感列表必须是边沿；always_comb 自动推导敏感列表、在 time 0 执行一次、禁止在别处驱动同一变量、若不完整赋值综合工具会警告 latch；always_latch 显式表明意图。三者让 lint/综合能检查意图与实现不一致。

延伸：阻塞/非阻塞赋值在 always_ff 中混用后果；always_comb 与 always @* 差异（对函数内部读取的变量敏感）；四态与二态（bit/int）在验证里的取舍（二态快但丢 X）。
interface、modport、clocking block 各解决什么问题？

interface 把一组信号打包，DUT 和 TB 共享同一定义；modport 限定方向（DUT 视角 vs TB 视角），防止 TB 误驱动；clocking block 定义采样/驱动相对时钟边沿的 skew（default input #1step output #0 或 #1），消除 TB 与 DUT 在同一边沿的竞争（TB 在时钟沿前 1step 采样得到"上一拍"的稳定值，驱动在沿后），并让同一 TB 在 RTL 和带 SDF 的 GLS 下都能正确工作。

延伸：#1step 的含义（前一个时间步的最后一个 postponed 区域）；clocking block 里不能直接读被驱动信号的当前值；虚接口在参数化 interface 下的类型匹配。
SystemVerilog 的事件调度区域（active/inactive/NBA/observed/reactive/postponed）与竞争？

每个时间步：Preponed（采样 SVA/clocking 输入）→ Active（阻塞赋值、连续赋值、$display）→ Inactive（#0）→ NBA（非阻塞更新）→ Observed（断言求值）→ Reactive（program/clocking 驱动、断言 action block）→ Re-inactive → Postponed（$strobe、$monitor）。竞争的根源是同一区域内顺序不确定；TB 用 clocking block/program（reactive 区域）在设计（active 区域）之后执行，避免采到未更新的值。

延伸：为什么 $display 在 NBA 前看到旧值；#0 为什么是坏习惯；UVM 为什么不推荐 program block。
fork...join / join_any / join_none 与 disable fork、wait fork；进程里的常见坑？

join 等全部；join_any 任一完成就往下走，其余仍在跑；join_none 立即往下走。清理用 disable fork（杀掉当前进程的所有子进程——所以要包一层 fork begin ... end join 防止误杀兄弟进程）或 process 句柄 kill()；wait fork 等所有子进程。坑：for 循环里 fork join_none 引用循环变量要用 automatic 局部变量拷贝；join_none 的子进程在父进程遇到阻塞语句前不会启动。

延伸：用 fork join_any 实现超时（fork begin task; end begin #timeout; end join_any disable fork）；semaphore/mailbox/event 的应用；wait(cond) vs @(posedge)。
SVA：immediate vs concurrent；|-> 和 |=>；常写的几条协议断言？

immediate 在过程块里像 if 一样立刻判；concurrent 基于时钟采样，用 sequence/property 描述多拍关系。|-> 同拍蕴含，|=> 下一拍蕴含。常写：valid 拉高后 ready 前不能撤（valid && !ready |=> valid && $stable(data)）；请求 N 拍内必须响应（req |-> ##[1:N] ack）；FIFO 满不写空不读；one-hot（$onehot0(sel)）；复位后信号为 0（$rose(rst_n) |-> !valid）；disable iff (!rst_n)。

延伸：断言里为什么避免 ##[0:$]（性能与永不失败）；assume/assert/cover 在仿真与 formal 中的意义；$past 在复位期间的行为；bind 的用法。
队列、动态数组、关联数组的区别与典型用途？

动态数组：连续、size 固定后随机访问 O(1)，用于长度可变的数据块（payload）；队列：两端 O(1) 插入删除，用于 FIFO/scoreboard 期望流、push_back/pop_front、支持切片和 find_with；关联数组：稀疏键值，用于按地址索引的内存模型、按 ID 索引的乱序事务表，遍历用 first/next。

延伸：数组的 foreach 对多维数组；sort/rsort/unique/sum with；关联数组默认值与 exists。
深拷贝与浅拷贝；为什么 UVM 的 copy/clone 要重载 do_copy？

句柄赋值只是指向同一对象；new obj2 = obj1 浅拷贝：成员里的句柄仍指向原子对象；深拷贝要递归复制。UVM 的 copy() 走 do_copy（或 field 宏），clone() = create + copy 返回 uvm_object 需要 $cast。monitor 里每次 write 前 clone 是因为下游可能保存句柄，下一次采样如果复用对象会被覆盖。

延伸：field automation 宏（`uvm_field_int）与手写 do_copy/do_compare/do_print 的性能差异；UVM_NOCOMPARE/UVM_NOPRINT 标志。
static 与 automatic；class 里的 static 成员与静态方法？

module 里的任务/函数默认 static，变量在所有调用间共享（递归和并发调用会踩数据），所以 TB 里用 automatic；class 方法默认 automatic。class 的 static 属性属于类本身（所有实例共享，如事务计数器 id），静态方法只能访问静态成员，可以不实例化调用（cls::method()）。

延伸：const、local/protected、纯虚方法与虚类（abstract）；参数化类的静态成员是每个特化一份。
DPI-C 怎么用？import/export、数据类型映射、常见问题？

import "DPI-C" function int c_add(input int a, b); 在 SV 里调 C；export "DPI-C" task sv_task; 让 C 回调 SV。类型映射：int↔int、longint↔long long、byte↔char、bit/logic 打包数组↔svBitVecVal/svLogicVecVal、string↔const char*、open array↔svOpenArrayHandle。用途：softfloat 参考模型、ISS（Spike）联合仿真、加载 ELF、C 测试驱动。问题：context 属性（需要访问 SV 作用域时 import "DPI-C" context）、多线程不安全、内存所有权、编译时 -LDFLAGS 链接。

延伸：DPI 与 PLI/VPI 的差别；用 DPI 时的性能考虑（批量传数据而不是逐拍调用）。
手写题：用 SV 写一个参数化同步 FIFO，并说明满/空判断和 almost_full。
module sync_fifo #(parameter W=8, D=16, AW=$clog2(D)) (
  input  logic clk, rst_n, wr_en, rd_en, input logic [W-1:0] din,
  output logic [W-1:0] dout, output logic full, empty, output logic [AW:0] count);
  logic [W-1:0] mem [D];
  logic [AW:0] wptr, rptr;                      // 多一位区分满空
  assign empty = (wptr == rptr);
  assign full  = (wptr[AW] != rptr[AW]) && (wptr[AW-1:0] == rptr[AW-1:0]);
  assign count = wptr - rptr;
  always_ff @(posedge clk or negedge rst_n)
    if (!rst_n) begin wptr <= '0; rptr <= '0; end
    else begin
      if (wr_en && !full)  begin mem[wptr[AW-1:0]] <= din; wptr <= wptr + 1'b1; end
      if (rd_en && !empty) rptr <= rptr + 1'b1;
    end
  assign dout = mem[rptr[AW-1:0]];               // first-word-fall-through
endmodule

满/空用指针多一位的 MSB 区分（D 为 2 的幂）；almost_full = count >= D-K，用于反压提前一拍。

延伸：异步 FIFO 的 Gray 码指针 + 两级同步器（你的 TetraMem CDC FIFO），为什么 Gray 码、为什么满空判断在跨域后是"保守"的；D 非 2 的幂怎么办。

D. CPU / RISC-V 微架构（JD："懂 CPU 的人：OoO pipeline、cache hierarchy、memory subsystem"）

Rocket 和 BOOM 的区别？MediumBoomConfig 是什么配置？

Rocket：RV64GC 顺序（in-order）5 级流水（PCGen/Fetch/Decode/Execute/Mem/WB，实际 IF→ID→EX→MEM→WB），单发射，非阻塞 D-cache，分支预测 BTB/BHT/RAS，支持 M/S/U 特权级、MMU（Sv39）；BOOM：RV64GC 乱序超标量（Fetch→Decode→Rename→Dispatch→Issue→RegRead→Execute→Memory→Writeback→Commit），物理寄存器堆 + 重命名 + ROB + 统一/分布式 issue queue、TAGE 分支预测、加载/存储队列。MediumBoomConfig：单个 BOOM tile，fetch 4 / decode 2、ROB 64、int/fp PRF 80/64、LDQ/STQ 16/16、issue queue mem 12 / int 20 / fp 16、maxBrCount 12、TAGE-L 预测器、16 KB 4 路 I$/D$（2 MSHR），带 FPU；是 BOOM 家族里"能在课程周期内流片"的中间档（Small 是 1 发射 ROB 32，Large 是 3 发射 ROB 96）。

延伸：Rocket 的 D-cache 为什么非阻塞（miss 下继续 hit，MSHR）；BOOM 的 execute pipeline 为什么把 ALU 延迟对齐到 iMul/FPU（共享写回口）；Chisel 生成的 Verilog 为什么难读（名字自动生成，firrtl 优化后展开）。
经典 5 级流水线的三种冒险及解决方法？

结构冒险：资源冲突（单端口存储器），解决：分离 I/D cache、多端口/复制；数据冒险 RAW：前递（EX→EX、MEM→EX），load-use 需插一拍 stall；WAR/WAW 在顺序流水线不出现，在乱序中用重命名消除；控制冒险：分支决议延迟，解决：分支预测（静态/动态 BHT、BTB、RAS）+ 误预测冲刷，或延迟槽。

延伸：验证角度怎么测前递：连续依赖指令序列 + ISS 比对；load-use 后紧跟 store 的 corner；异常在流水线中的精确处理（精确异常需在 commit 点统一处理）。
乱序核的重命名、ROB、issue queue、LSQ 各解决什么问题？

重命名（map table + free list + 物理寄存器堆）消除 WAR/WAW 假依赖；ROB 按程序序记录指令状态，保证精确异常和顺序提交，误预测时回滚 map table（或用 checkpoint/branch mask，BOOM 用 branch mask 快速 kill 所有被推测指令）；issue queue 保存等待操作数的指令，操作数就绪即唤醒发射（数据流执行）；LSQ 保证内存序：store 在 commit 后才写 cache（store buffer），load 可推测执行但要检查与更早 store 的地址冲突（memory disambiguation），冲突则重放/冲刷。

延伸：load 推测唤醒（假设 hit，miss 时重放）；memory ordering violation 检测；RISC-V 的 RVWMO 内存模型 + fence；验证 OoO 核时 trace-compare 为什么按 commit 序。
Cache 的组成、映射方式、写策略、替换策略、一致性？

地址 = tag | index | offset；直接映射/组相联/全相联，相联度高冲突少但比较器多、延迟功耗高；写策略：write-through（简单，需写缓冲）vs write-back（dirty 位，替换时写回）；写分配 vs 不分配；替换：LRU/PLRU（你写过 plru_4way.sv）/随机；一致性：多核用 MESI/MOESI 目录或监听，TileLink 用 Probe/Release 通道实现；I-cache 与 D-cache 的一致性依赖 fence.i；VIPT 用页内偏移做 index 避免别名问题（index+offset ≤ page size，否则需处理 aliasing）。

延伸：MSHR 与非阻塞 cache；预取器；cache 验证的测试点（hit/miss/evict/dirty writeback、同一行并发访问、miss under miss、错误注入 ECC）；Agent workload 提到的"内存访问模式不可预测"意味着什么（预取失效、TLB miss 多、需要更大 LLC / 更好的 replacement）。
虚拟内存与 TLB：页表遍历、TLB miss 的处理、验证要点？

RISC-V Sv39 三级页表，satp 指向根页表；TLB 缓存 VA→PA 映射与权限位；miss 时硬件 PTW 逐级读内存（Rocket 有硬件 PTW，共享 L1 D-cache 或 L2），缺页/权限错触发 page fault 异常交给 OS。验证要点：各种权限组合（R/W/X/U/A/D 位）、超页（megapage/gigapage）、TLB 替换、satp 切换后 sfence.vma、PTW 期间的异常、两级地址翻译（H 扩展）。

延伸：A/D 位硬件更新 vs 软件更新（Svadu）；ASID；PMP 与 PMA 检查的顺序。
RISC-V 特权级、CSR、异常/中断处理流程？

M/S/U 三级；异常发生时：把 PC 存 mepc、原因存 mcause、附加信息 mtval、保存并关闭中断使能（mstatus.MPIE ← MIE, MIE ← 0、MPP ← 当前特权级）、跳到 mtvec（direct/vectored 模式）；mret 恢复。中断有 M/S 级的 software/timer/external 三类，由 mie/mip 与 mideleg/medeleg 委托到 S 模式。验证：每种异常的优先级、同时发生时的选择、委托、WFI、中断在流水线中的精确性（不能在指令中间响应）。

延伸：CSR 的 WARL/WLRL 语义（你在 RAL 里建模过）；fcsr={frm,fflags} 别名；计数器 mcycle/minstret 的 volatile 建模；CLINT/PLIC 的作用。
分支预测器有哪几类？误预测的代价和恢复？验证怎么覆盖？

静态（BTFN）、1/2-bit 饱和计数器 BHT、gshare（全局历史 XOR PC）、tournament、TAGE（多长度历史的 tagged 表，BOOM 用）、BTB（目标地址）、RAS（返回地址）、loop predictor。代价 = 前端到决议点的流水级数；恢复：冲刷所有更年轻指令、恢复 rename map（checkpoint 或 walk ROB）、恢复 RAS。验证覆盖：taken/not-taken 各种模式、BTB 别名、RAS 溢出/下溢、间接跳转、误预测与异常同时、预测器在复位后的状态。

延伸：预测器只影响性能不影响功能，怎么验证性能（性能计数器 + 参考模型/性能模型对比，trace 驱动）；Agent workload "推理与逻辑交织"对分支预测的挑战。
Agent workload（多轮推理、工具调用、RAG）"延迟敏感、频繁上下文切换、内存访问不可预测"对 CPU 微架构和验证意味着什么？

微架构上可能的方向：更大/更智能的 LLC 与更强的 memory-level parallelism（更多 MSHR、更深 LSQ）、减少上下文切换开销（更大 TLB、ASID/PCID 避免刷 TLB、快速的寄存器保存/恢复、更多硬件线程）、面向指针追逐（pointer chasing）的预取、大量分支/短函数调用的前端（大 BTB、返回栈、指令预取）、低延迟的核间通信与中断。验证意义：性能验证成为一等公民——需要 trace 驱动的性能回归、性能计数器验证、在 FPGA/emulator 上跑真实 agent trace；功能验证要重点覆盖 TLB/ASID 切换、并发中断、大 outstanding miss 下的一致性。

延伸：你会怎么设计一个"性能 scoreboard"（对比 IPC、miss rate 与性能模型，容差判定）；hardware/software co-design 中 verification-in-the-loop 的含义（RTL 改动即刻用同一 workload 验证性能与功能）。
存储器验证（SRAM/DDR 控制器）关注什么？

SRAM：读写冲突（同拍同地址读写行为，read-first/write-first）、字节使能、掩码、ECC 编码/解码/单纠双检、BIST、行为模型与编译器生成的 macro 的一致性（Chipyard 的 top.mems.v 就是行为模型，流片要换成 SRAM compiler 输出并做 LEC/仿真）。DDR 控制器：初始化序列、刷新、时序参数（tRCD/tRP/tRAS/tWR）、bank 管理、读写调度公平性、数据完整性（用行为级 DRAM 模型 + scoreboard）、低功耗状态、训练。

延伸：怎么验证 SRAM 替换后功能一致（黑盒 LEC + 定向读写）；memory model 用 DPI 大数组还是关联数组；ECC 错误注入。

E. 总线与高速接口（AXI/AHB、PCIe、DDR、TileLink）

AXI4 的五个通道和握手规则；你的 2M×3S 环境怎么验证互连？

AW/W/B（写地址/写数据/写响应）、AR/R（读地址/读数据），每通道独立 valid/ready 握手：valid 不得依赖 ready，valid 拉高后不能撤且数据保持；同一 ID 的事务必须按序响应，不同 ID 可乱序；写数据可先于写地址；burst 类型 FIXED/INCR/WRAP，4KB 边界不可跨；WSTRB 字节使能；RESP OKAY/EXOKAY/SLVERR/DECERR。2M×3S 环境：每个 master 一个 active agent、每个 slave 一个带内存模型的 responder（或 passive+行为 slave）；scoreboard 按地址译码预测目标 slave，检查数据一致、ID 顺序、DECERR（未映射地址）；覆盖 burst 类型×长度×size×未对齐、两 master 同时访问同一 slave 的仲裁、outstanding 深度。

延伸：AXI 死锁场景（写数据交织 WID 在 AXI4 已取消）、AXI3 vs AXI4 区别、AXI-Lite/AXI-Stream；exclusive access；QoS/region；interconnect 的 ordering 检查为什么难。
AHB 与 AXI 的区别？什么时候用 AHB？

AHB：单通道地址/数据、两级流水（地址阶段与数据阶段重叠）、HREADY 统一等待、无 outstanding（一个 master 一笔在途）、burst 简单，适合低功耗 MCU 外设总线；AXI：五通道分离、多 outstanding、乱序、读写并行，适合高性能。APB 更简单用于寄存器配置。

延伸：AHB-Lite 与 multi-layer AHB；AXI→APB 桥的验证要点（响应转换、错误映射）。
TileLink 是什么？和 AXI 相比有什么特点？

Chipyard/Rocket 内部互连协议，五个通道 A（请求）/B（probe）/C（release）/D（响应）/E（ack），TL-UL/TL-UH/TL-C 三个等级，TL-C 内建 cache 一致性（Acquire/Probe/Release），消息按 size/mask/source/sink 组织，保证无死锁的优先级 A<B<C<D<E。与 AXI 相比：内建一致性、更规则的握手（同样 valid/ready，但 ready 可依赖 valid 的规则更明确）。Chipyard 通过 TL→AXI4 桥接外设/DDR。

延伸：怎么给 TileLink 写 monitor 与断言（Chipyard 自带 TLMonitor）；Acquire 的权限升级/降级。
PCIe 的分层结构和验证关注点？

事务层（TLP：Memory/IO/Config/Message，含 header/payload/ECRC，流控 credit）、数据链路层（DLLP、ACK/NAK、重传、序列号、LCRC）、物理层（LTSSM 链路训练：Detect→Polling→Configuration→L0，8b/10b 或 128b/130b 编码、lane 反转/极性、速率协商、均衡）。验证关注：LTSSM 所有状态转移与超时、流控 credit 更新、乱序/重传、TLP 格式与错误（毒化、ECRC、malformed）、配置空间与能力结构、电源状态 L0s/L1/L2、MSI/MSI-X 中断、多功能/SR-IOV；通常用商用 VIP（Synopsys/Cadence）+ 自定义 sequence，系统级 DMA 数据流 scoreboard。

延伸：PIPE 接口是什么（MAC 与 PHY 分离，仿真时可绕过 SerDes）；Gen3 以上均衡训练验证；错误注入与 AER。
DDR（如 DDR4/LPDDR4）接口验证关注点？

控制器侧：初始化/训练（ZQ、write leveling、read gate、read/write DQ 训练）、命令时序（tRCD/tRP/tRAS/tRRD/tFAW/tWTR）、刷新（REF、per-bank refresh）、bank group、地址映射、读写调度与 QoS、ECC、低功耗（self-refresh、power-down）、DBI/CRC/parity。验证方式：用 Micron 行为模型或商用 DRAM VIP 检查协议时序（模型自带 timing check），控制器前端用 AXI agent 做数据完整性 scoreboard，覆盖各类 timing 参数边界与 page hit/miss/conflict 场景。

延伸：PHY 与控制器的 DFI 接口；为什么 DDR 的时序违例仿真里只能靠模型 check；gate-level 下的 DDR IO 时序。
跨时钟域（CDC）的验证怎么做？

静态：CDC lint 工具（SpyGlass/Questa CDC/Jasper CDC）检查同步器缺失、收敛（reconvergence）、数据总线未握手、复位同步；结构：单 bit 用两级同步器、多 bit 用握手/异步 FIFO（Gray 指针）/ MCP（multi-cycle path）方案；仿真：随机时钟相位/频率比、亚稳态注入模型（对同步器输出随机延一拍）、在 GLS 下检查；断言：跨域信号在被采样前保持稳定（$stable）、Gray 码每拍只变 1 位。你的 TetraMem 系统在两个时钟比下回归就是这个思路。

延伸：为什么快到慢的脉冲要展宽或用握手；复位域交叉（RDC）；异步 FIFO 的空/满判断是保守而非错误。

F. Formal / JasperGold（加分项）

形式验证和仿真的本质区别？什么类型的模块适合 formal？

仿真是采样式（跑过的路径才被检查），formal 是穷举式（对所有输入序列证明性质成立，或给出反例），不需要激励但需要约束（assume）避免非法输入；受状态空间限制，深度有限。适合：仲裁器、FIFO、总线协议桥、握手/控制逻辑、寄存器访问（CSR 权限）、死锁/活锁、安全属性（隔离）、连接性检查、X 传播、等价检查（LEC/SEC）；不适合：大数据通路（乘法器需抽象）、深序列（DDR 初始化）、软件流程。

延伸：bounded proof 与 full proof 的区别；formal coverage（cone of influence、proof core）；怎么防止过约束（assume 太强 → cover 检查可达性）。
JasperGold 的基本流程和常用 app？

流程：analyze 读 RTL → elaborate -top → clock/reset 定义 → 写 SVA（assert/assume/cover）或 bind → prove -all → 分析结果（proven/cex/undetermined），反例用波形调试，undetermined 通过增加 engine 时间、抽象（黑盒存储、cut point、初始状态约束）、分解性质来收敛。Apps：FPV（属性验证）、CDC/RDC、CONN（连接性）、SEC（时序等价）、XPROP、CSR（寄存器）、SPV（安全路径）、Coverage、Unreachability（UNR，找不可达覆盖点）。

延伸：你用 Jasper 验证过什么（如 FIFO 不溢出、仲裁公平性）；怎么用 cover 证明环境没过约束；abstraction（计数器抽象、memory 抽象）。
给一个仲裁器写 formal 属性，你会写哪些？

安全性：任一时刻最多一个 grant（$onehot0(gnt)）；grant 必须对应 request（gnt[i] |-> req[i]）；活性：请求最终被授权（req[i] |-> s_eventually gnt[i]，或有界版本 ##[1:N]）；公平性/轮转：round-robin 时同时请求下上一次被授权者优先级最低；无 grant 时无 req；cover：所有请求同时到达、连续授权同一 master 等场景可达。假设：req 不在 grant 前撤（若协议要求）。

延伸：liveness 需要 fairness 假设；为什么 s_eventually 在仿真中难以检查而在 formal 中可以。

G. STA · 时钟 · 低功耗 · 后端常识（验证工程师应知）

setup/hold 的公式，违例分别怎么修？

setup：Tclk + Tskew ≥ Tcq + Tlogic + Tsetup + Tuncertainty，slack = required − arrival；hold：Tcq + Tlogic ≥ Thold + Tskew。修 setup：减逻辑深度（重定时、流水线）、升驱动、减负载、useful skew、降频、优化布局；修 hold：插 delay/buffer（项目中 freepdk 无 delay cell 只能用 buffer）、调 clock skew；hold 不能靠降频修，且要在所有角修（通常在 best corner 最严重）。

延伸：为什么 CTS 后才修 hold；multi-cycle / false path 约束的验证风险（约束错了仿真也抓不到，需要 GLS with SDF）；OCV derate。
时钟树综合的目标？clock gating 对验证的影响？

CTS 目标：控制 skew、latency、transition，插入平衡的 buffer 树（CCOpt 同时做 useful skew 优化）；ICG 插入（综合 lp_insert_clock_gating）把 if (en) q<=d 变成门控时钟，省动态功耗。对验证：门控后的时钟在仿真中"停"了，RTL 与门级行为等价但 GLS 中若 ICG 使能有 glitch（latch-based ICG 能防）会导致 X；LEC 需要识别 ICG 的等价；覆盖率要覆盖 gating on/off；功耗估算要有真实 activity。

延伸：CTS 为什么在 place 之后 route 之前；skew 与 useful skew；clock gating 的 test mode 旁路（DFT）。
低功耗设计技术与 UPF 验证？

技术：clock gating、多电压域（level shifter）、power gating（isolation cell、retention 寄存器、power switch）、DVFS、多 Vt 单元、时钟/存储器休眠。UPF/CPF 描述电源意图；验证：低功耗仿真（VCS NLP/Xcelium LPS）按 UPF 关电时把域内信号置 X、检查 isolation/retention 时序（先隔离再断电，先上电再解隔离）、状态机覆盖所有电源状态转换、静态检查（UPF lint）。项目里 commit_power_intent 步骤对应读入电源意图，但这颗 BOOM SoC 只有单电源域。

延伸：ICG 与 power gating 的验证差异；always-on 逻辑；retention 寄存器的保存/恢复序列断言。
综合会做哪些优化？为什么综合后的网表要 LEC 而不是靠仿真？

常量传播、死逻辑删除、寄存器合并/复制、FSM 重编码、资源共享、重定时（若开启）、时钟门控插入、boundary optimization（层次边界穿越，flatten_effort 控制）、DesignWare/ChipWare 算术单元映射。LEC 能穷举证明结构等价，仿真只能抽样且门级仿真慢几十倍；但 LEC 不检查 X 行为和时序，所以 GLS 仍然需要一小部分（复位、时钟、DFT）。

延伸：综合无法处理的 RTL 结构（initial、#延迟、非阻塞混用）；lint（SpyGlass）在 RTL 阶段抓什么；同步复位与异步复位的综合差异与验证（复位释放的 CDC）。
DFT 基本概念：scan、ATPG、BIST，验证工程师参与什么？

Scan 把触发器串成移位链，测试模式下移入 pattern、capture、移出比较；ATPG 生成 pattern，覆盖 stuck-at/transition fault；MBIST 对存储器用内置状态机跑 March 算法；JTAG/TAP 控制。验证参与：scan 插入后网表的 GLS（shift/capture 模式）、ATPG pattern 的 Verilog 仿真（零延迟 + SDF）、MBIST 控制器功能验证、测试模式下的时钟/复位切换（占 GLS 失败大头）。

延伸：scan chain 对 LEC 的影响（test mode 约束为 0 做等价）；带 SDF 的 ATPG 仿真为什么会挂（hold 违例、X 源、时序检查）。

H. 脚本与 C（Python / Tcl / Perl / Makefile）

你用 Python/Tcl 做过什么自动化？举一个具体例子。

Python：cat-files.py 把 .f 列表拼成单文件；generate-setup-yaml.py 从 adk.tcl 解析变量生成 SFK 配置；回归脚本（并行跑 seed、解析 log、汇总覆盖率、生成 HTML）；测试向量生成（GcdUnit 的 generate_test_vectors.py）。Tcl：mflowgen 节点里所有 EDA 脚本（Genus/Innovus/Conformal），dbGet→get_db 翻译、flow_step 定义。Makefile：mflowgen 生成的 DAG 依赖、UVM 仿真的 questa/vcs/xcelium 目标。

延伸：手写题：用 Python 解析仿真 log 统计每个 test 的 UVM_ERROR 数并输出表格（正则 + dict + csv）；用 Tcl 写一个遍历 get_db insts 过滤 FILL* 的 proc；Perl 的正则一行式。
手写题：Python 解析 log 汇总回归结果。
import re, glob, collections, csv
pat_err  = re.compile(r'UVM_ERROR\s*:\s*(\d+)')
pat_test = re.compile(r'\+UVM_TESTNAME=(\w+)')
rows = []
for f in glob.glob('logs/*.log'):
    txt = open(f, errors='ignore').read()
    test = (pat_test.search(txt) or [None, f])[1]
    errs = int(pat_err.search(txt).group(1)) if pat_err.search(txt) else -1
    seed = re.search(r'seed=(\d+)', txt)
    rows.append((test, seed.group(1) if seed else '?', 'PASS' if errs == 0 else 'FAIL', errs))
by_test = collections.Counter(r[0] for r in rows if r[2]=='FAIL')
with open('summary.csv','w',newline='') as fp: csv.writer(fp).writerows([('test','seed','status','errors'),*rows])
print(sorted(by_test.items(), key=lambda kv: -kv[1]))
延伸：怎么并行跑（subprocess + concurrent.futures）；怎么把 seed 失败的复现命令直接打印出来；用 argparse 参数化。

I. FPGA 原型 / 硬件加速 / 系统级（JD 职责 3、4）

仿真、emulation、FPGA 原型各自定位？在 FPGA 上复现问题怎么做？

仿真：可观测性最好、最慢（kHz），用于模块级/系统级功能；Emulation（Palladium/Zebu/Veloce）：MHz 级、可编译整芯片、有波形/断点，用于软件启动、长 workload；FPGA 原型：几十 MHz、最接近真实、观测性差，用于软件开发、接口互操作。FPGA 复现：先用 ILA/ChipScope 抓触发条件附近波形，或用 trace buffer 记录 commit log；把问题缩小到可在仿真复现的序列（导出寄存器状态/内存镜像做仿真初始状态，或用 riscv-dv 生成同类指令流）；注意 FPGA 的 RAM 初始化、时钟比、异步接口与 ASIC 的差异导致的"只在 FPGA 出现"的问题。

延伸：FireSim（Chipyard 的 FPGA 加速仿真，cycle-exact）；同一 RTL 在 FPGA 上需要哪些修改（时钟、存储、IO、复位）；hybrid（部分 emulation + 部分 VIP）。
系统级验证怎么组织？软件测试与 UVM 怎么配合？

系统级以 C 测试/固件驱动为主：启动 → 配置外设 → 数据流（DMA、以太网、PCIe）→ 中断 → 低功耗；UVM 提供外部接口 agent（DDR 模型、PCIe VIP、UART 监视）和被动检查；同步机制：软件写 mailbox 寄存器触发 UVM sequence，或 UVM 通过 DPI 读取软件状态；scoreboard 做端到端数据流检查；覆盖率关注集成点。回归按 test list 分层（smoke/nightly/weekly），失败自动 triage（按错误签名聚类）。

延伸：怎么做"验证质量与进度把控"（vplan 完成率、覆盖率曲线、bug 趋势、review checkpoint）；系统级 X 传播（复位未初始化的 RAM）。
协助设计定位缺陷：你怎么写一份高质量的 bug report？

标题一句话（模块 + 现象）；复现步骤（test、seed、命令、commit hash）；期望 vs 实际（引用 spec 条款）；最小化：缩到最短序列、关掉无关随机；波形定位（时间戳、信号名、截图/路径）；初步分析（怀疑 RTL 哪一行、或验证环境问题的排除证据）；影响范围与优先级；关联 issue。BOOM tapeout 项目里的习惯：日志拷贝存档、用 flowtool -from/-to 80 秒复现。

延伸：怎么判断是 TB bug 还是 RTL bug（参考模型独立、第二种检查方式、与 spec 核对）；bug 修复后怎么防回归（把复现 case 加进回归 + 加断言）。
