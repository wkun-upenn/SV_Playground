The BOOM Core — Execution Logic, Explained

An interactive tour of the Berkeley Out-of-Order Machine (RV64GC): the 10-stage pipeline, the execute cluster, register renaming, the reorder buffer, the CSR path, and IEEE-754 floating point with all its corner cases. Built from the official BOOM documentation.

The BOOM Pipeline at a Glance

Conceptually BOOM has 10 stages: Fetch, Decode, Rename, Dispatch, Issue, Register Read, Execute, Memory, Writeback and Commit. The implementation folds these into 7 physical stages (Decode/Rename and Rename/Dispatch combine; Commit happens asynchronously). Everything up to Issue runs in order; Issue is where the machine goes out of order; Commit puts the illusion of program order back.

In-order front, out-of-order middle, in-order retire

The front-end fetches instructions into a Fetch Buffer while branch prediction (BTB + gshare/TAGE) steers the PC. Decode cracks them into micro-ops (uops). Rename maps ISA registers onto a large Physical Register File (PRF) — BOOM is an explicit renaming design like the MIPS R10k and Alpha 21264. Dispatch writes uops into the ROB (for ordering) and into Issue Queues (for scheduling). From there, uops issue whenever their operands are ready — this is where program order stops mattering — flow through Register Read into the Execution Units, and write results back to the PRF. The ROB commits finished instructions strictly in order.

Every in-flight uop carries a branch mask — one bit per unresolved branch it is speculated under. When a branch resolves correctly, that bit clears everywhere. When it mispredicts, every uop with that bit set is killed in one cycle, and the rename map is restored from the branch's snapshot.

The Execute Pipeline

Each issue port feeds exactly one Execution Unit (EU); an EU wraps a mix of Functional Units (FUs). A dual-issue BOOM typically pairs EU#0 = ALU + FPU + iMul with EU#1 = ALU + iDiv + address-gen/LSU. Try the buttons — they animate a uop through the cluster below.

Hover any block for its role. Solid-border FUs are pipelined (accept a uop every cycle); dashed FUs are un-pipelined (go busy, back-pressure the issue queue).

Pipelined vs un-pipelined functional units

Pipelined FUs (ALU, iMul, FPU) accept a new uop every cycle with a fixed latency. BOOM auto-generates a shadow pipe that carries the uop's metadata and branch mask alongside the expert-written datapath (borrowed from Rocket/hardfloat); if the uop is misspeculated, its response is simply gated off as it exits. Un-pipelined FUs (integer divider, FDiv/Sqrt) take a variable number of cycles and de-assert their ready bit in the EU's readiness vector while busy, so the issue scheduler stops sending that class of uop.

A classic BOOM trick: the ALU's 1-cycle result is padded with pipeline registers to match the FPU/iMul latency, so all pipelined FUs in an EU can share one register-file write port without any arbitration. ALU results still bypass to dependent instructions from the early stages — you get back-to-back dependent adds — but the write port sees a perfectly scheduled single stream.

The Branch Unit

One EU hosts the Branch Unit. On a correct prediction it just broadcasts "branch tag N resolved" and every uop clears bit N of its branch mask. On a mispredict it redirects the PC immediately, kills the front-end, and broadcasts the tag so all dependent uops die — the kill broadcast is pipelined one cycle for timing. Jump-registers are verified against the PC of the next instruction stored in the ROB's PC file.

The CSR path (why CSRs need no renaming)

Control/Status Register instructions (csrrw/csrrs/csrrc) execute in the Rocket-derived CSRFile. BOOM does not rename CSRs; instead a CSR instruction is marked "unique" / serializing: the ROB must drain completely before it issues, and nothing dispatches behind it until it commits. It reads its operand from the PRF, executes in the CSRFile (possibly raising an exception or redirecting the PC — think ecall), and writes the old CSR value back to its destination register. Slow, but trivially correct — and CSR ops are rare.

FDiv/Sqrt: the awkward guest

The double-precision divide/sqrt unit from hardfloat is un-pipelined and has an unstable FIFO interface — it may be ready this cycle and not the next, even with no new work. BOOM buffers instructions inside the wrapper and applies back-pressure to the issue queue when that buffer fills. Single-precision operands are upscaled to double, computed, and downscaled — cheaper than a second SP unit.

Register Renaming

Renaming maps the 32 ISA ("logical") registers x0–x31 onto a much larger pool of physical registers (e.g. ~100 for the integer PRF). Why? Because only true data dependences (RAW) are fundamental. The other two hazard types are artifacts of register-name reuse, and renaming simply deletes them:

HazardMeaningAfter renaming
RAW (read-after-write)true dependence — consumer needs the producer's valuekept (this IS the dataflow)
WAW (write-after-write)two writers reuse the same namegone — each write gets a fresh preg
WAR (write-after-read)a later write would clobber an earlier readergone — the reader keeps its old preg

Three structures do the work. The Rename Map Table holds the current speculative mapping xN → pM. The Free List (a bit-vector with a priority decoder) hands out unused physical registers. The Busy Table says which physical registers still await their value — when all of a uop's source pregs are un-busy, it can issue.

The stale physical destination ("stale pdst")

  
When an instruction that writes xN is renamed, the map table is read
  first to capture the old mapping — the stale pdst. That old physical
  register can't be freed yet: an earlier-in-flight instruction might still read it, and
  if we flush, the old mapping is the architectural state. Only when the new
  instruction commits is the stale pdst returned to the Free List. This is
  exactly what the ROB stores per entry: logical dest + stale pdst.


  
Branch snapshots & misprediction recovery

  
Every branch (and JALR) snapshots the entire Map Table and starts an
  Allocation List in the Free List — a running record of every preg allocated
  after that branch. On a mispredict, recovery is single-cycle: the Map Table is reset
  from the branch's snapshot, and the Allocation List is OR-ed back into the Free List
  (a naive "snapshot the free list" scheme leaks registers — a preg freed after
  the snapshot then re-allocated would be lost; the original BOOM author hit exactly
  this bug). An optional Committed Map Table gives the same single-cycle reset
  for exceptions and pipeline flushes.


  
Because RV64G puts register specifiers at fixed bit positions, the
  Map Table can be read before the instruction is even fully decoded — which is
  why BOOM merges Decode and Rename into one stage.







  
The Reorder Buffer — putting order back

  
The ROB tracks every in-flight instruction and provides the illusion of in-order
  execution. Uops are written at the tail at dispatch and marked busy;
  they clear busy when they finish executing (in any order!); the head commits
  instructions only in program order. For a 2-wide BOOM the ROB is a circular buffer of
  W-wide rows — one row per fetch group, so a single PC serves the whole row and
  dispatch/commit move a full row at a time.

What one ROB entry holds

  
Surprisingly little: valid, busy, is-exception, the branch mask, the rename
  state (logical dest + stale pdst — needed to free registers at commit and to
  unwind on flushes), and FP status updates. The PC is stored once per row in a
  separate PC File (branches read it at Register Read to compute targets), and full
  exception detail (cause, bad address) is kept only for the oldest excepting
  instruction — younger ones may be squashed anyway, so storing theirs would be waste.


  
Commit, exceptions, and the two unwind strategies

  
When the head entry is done and not excepting, it commits: its architectural change
  becomes visible, its stale pdst is freed, and (for stores) the LSU is told it may
  drain the store to memory. If the head is excepting, the pipeline flushes and the
  rename map must be restored to the committed state — either by rolling back the
  ROB one row per cycle (writing each stale pdst back into the map, R10k-style) or in a
  single cycle from the Committed Map Table if that option is enabled.


  
A newer pointer, the PNR (point of no return), runs ahead of the commit head
  marking instructions that can no longer be misspeculated or fault. Instructions between
  head and PNR are guaranteed non-speculative even before writing back — BOOM uses this
  to launch RoCC co-processor instructions safely.

RISC-V NaN rules BOOM follows: any NaN result is the
  canonical qNaN 0x7FF8_0000_0000_0000 — NaN payloads are not
  propagated. Single-precision values stored in the 64-bit FP registers are
  NaN-boxed (upper 32 bits all-ones); a wrongly-boxed input is treated as qNaN.
  The five accrued exception flags in fflags are NV invalid,
  DZ divide-by-zero, OF overflow, UF underflow, NX inexact —
  they only accumulate (sticky) and are read/cleared through the fcsr/fflags
  CSRs. Because writing them is a CSR op and setting them is an FP-writeback side
  effect, fflags is exactly the kind of "volatile" register a UVM RAL model must
  mark as such.


  
FCLASS — the classifier instruction

  
fclass.d returns a 10-bit one-hot: −inf, −normal, −subnormal, −0, +0,
  +subnormal, +normal, +inf, sNaN, qNaN. It's the cheapest way for software (and for a
  verification scoreboard) to bucket operands — the UVM coverage model in the
  companion testbench crosses exactly these classes against every FP op.


  
Rounding modes (frm)

  
frm holds RNE (round-to-nearest-even, the default), RTZ (toward zero),
  RDN (toward −∞), RUP (toward +∞), RMM (to nearest, ties away). Instructions can also
  encode DYN to use frm. Rounding mode changes which corner you land on:
  1e308 − 1e308·(1−ε) is +0 under RNE but −0 under RDN.


  
Inside the FPU — how add and multiply actually work

  
Every pipelined FP op walks the same five stations:
  unpack (split sign/exponent/significand, restore the implicit 1, branch off
  the special cases) → align or multiply → normalize (put the result
  back into 1.xxx form) → round (RNE using guard + sticky bits) →
  pack. Two fully worked examples, every bit real
  (div/sqrt are different: they grind one result bit per cycle in the un-pipelined
  FDiv/Sqrt unit instead):


  

    
Worked example 1 — FADD.D: 2.25 + 1.5

    
a = fl(2.25) = 0x4002_0000_0000_0000 = 1.001₂ × 2¹
b = fl(1.5)  = 0x3FF8_0000_0000_0000 = 1.1₂   × 2⁰

    

      
StepWhat happensValues

      
1. Unpacksplit sign/exp/mantissa, restore the implicit 1,
          check specials (none here)
          e_a=1, e_b=0

      
2. Alignexponent difference = 1 → shift the smaller
          operand's significand right 1 so both share exponent 2¹. Any bits that fall off
          the right end would be compressed into the sticky bit — this is where
          precision is lost when the exponents are far apart (add a tiny number to a huge
          one and the small significand shifts away entirely).
          b → 0.11₂ × 2¹

      
3. Addone wide integer addition of the aligned significands
          (same-sign add; effective subtraction would instead cancel and possibly need a
          big left-shift)
          1.001 + 0.110 = 1.111₂ × 2¹

      
4. Normalizesum is already in [1,2) → no shift
          (a sum ≥ 2 would shift right 1 and bump the exponent)
          —

      
5. Roundguard=0, sticky=0 → nothing was shifted out,
          nothing to round: the result is exact, no flags at all
          NX=0

      
6. Packreassemble sign/exp/mantissa
          0x400E_0000_0000_0000 = 3.75 ✓

    

    
Same values in FP32: 2.25 = 0x4010_0000,
    1.5 = 0x3FC0_0000, 3.75 = 0x4070_0000 — identical steps,
    just bias 127 and a 23-bit mantissa.

  


  

    
Worked example 2 — FMUL.D: 2.25 × 2.25

    
a = b = fl(2.25) = 0x4002_0000_0000_0000 = 1.001₂ × 2¹

    

      
StepWhat happensValues

      
1. Unpacksplit fields; specials would branch off here
          (inf×0 → qNaN+NV …)
          e=1 each

      
2. Sign / exponentsign = s_a ⊕ s_b; exponents simply
          add (no alignment needed — this is why FP multipliers are structurally
          simpler than adders)
          s=0, e = 1+1 = 2

      
3. Multiplyinteger multiply of the significands
          (53×53 → up to 106 bits in hardware; here 1001₂ × 1001₂ = 1010001₂);
          this multiplier array is the big silicon of the FPU and the core of the FMA unit
          P = 1.010001₂  ((9/8)² = 1.265625)

      
4. Normalizea product of [1,2)² lands in [1,4);
          here P < 2 → no shift (if P ≥ 2: shift right 1, exponent+1)
          —

      
5. Roundeverything below bit 52 is zero → guard=0,
          sticky=0 → exact, no flags
          NX=0

      
6. Packreassemble
          0x4014_4000_0000_0000 = 5.0625 ✓ = 1.010001₂ × 2²

    

    
Why these examples are exact — and most aren't: 2.25 and 1.5
    have short binary fractions, so nothing ever falls off the end of the datapath.
    Feed the same pipeline decimal-friendly values instead and rounding appears at step 5:
    fl(16.9) × fl(16.9) ends one ulp below fl(285.61)
    (so 16.9 × 16.9 == 285.61 is false in floating point!), while
    sqrt(fl(285.61)) lands one ulp above fl(16.9) — both
    correct per IEEE-754, with NX=1. Verification lesson: a scoreboard must predict the
    correctly-rounded result of the actual binary inputs (softfloat-style, bit-exact),
    never the decimal answer a human expects — otherwise it fails correct RTL by one ulp.
