What the DUT computes

C = A×B for signed matrices, done as a stream: each cycle the DUT receives one column of A and one row of B, and accumulates their outer product. After M such cycles (M = contraction dimension, 1…N, supplied as M_minus_one at the sub-system level), the N×N result C is complete and streams out one row per cycle. Element width is DIN_WIDTH=8; accumulators and C elements are 2*DIN_WIDTH=16 bits and wrap on overflow — the golden model reproduces that wrap exactly.

The key identity behind everything: C = Σk (A column k)(B row k) — a sum of M rank-1 updates. It is what the physical PE mesh computes distributed in space, what the behavioral model computes per cycle, and what makes the golden model a ten-line function.

Two tracks were built

track A · optional RTL · rtl/ + tb/

Synthesizable-style RTL, verified with Verilator

The assignment says RTL is not required — it was built anyway to have something concrete to regress against: a weight-stationary pe with double-buffered weights, an N×N mesh with input skew / output de-skew (out_valid = in_valid delayed 2N−1), a Cummings-style Gray-pointer async_fifo, a 6-state controller FSM, and a column→row data_align transpose buffer. Self-checking SV testbenches: PE (807 checks), array at N∈{1,2,3,4,8}, sub-system across a reversed clock ratio — all pass.

track B · the deliverable · uvm/

UVM 1.2 environment on Cadence Xcelium 25.03

One environment verifies both DUT levels at once: an array agent plus two sub-system channel agents (write / read), monitor-side golden prediction, one reusable scoreboard class instantiated per level, three covergroups, a virtual sequencer for multi-channel stimulus, and nine tests. The DUTs here are compact behavioral models honoring the exact page-11/12 interfaces — swapping in the track-A RTL is only a tb_top instance change.

Track A: the real RTL (rtl/)

pe.sv — the processing element

A weight-stationary MAC cell. a flows left→right (registered pass-through), the partial sum flows top→bottom as c_out = a·w + c_in (registered). The weight is double-buffered: ld_w writes the inactive w_load register while the array computes with w_active; a one-cycle swap_w pulse promotes it — so a new B matrix takes effect with zero stall (the page-10 requirement).

systolic_array.sv — the N×N mesh

Weight-stationary mesh (3×3 shown, design is N×N). The triangular skew registers on the left and the de-skew registers at the bottom keep the external interface whole-row-in / whole-row-out.

  • Skew: a_din[r] is delayed r cycles so row i’s activation meets its partial sum that has traveled r hops down. The result of column c is delayed N−1−c on the way out so each c_dout beat is one aligned row of C.
  • Latency: out_valid = in_valid delayed exactly 2N−1 cycles (a simple shift register generates it).
  • Control strobes: the PDF lists no weight-load pins but says “control signals etc. are not listed” — two were added: w_load_en (qualifies b_din as sequential weight-load rows, an internal counter selects the PE row) and w_swap (activates the freshly loaded buffer).

sub_sys.sv — the streaming wrapper

The two async FIFOs do the CDC; everything between them lives on sr_clk. The controller stages weights and results in local registers, so an empty input FIFO or a full output FIFO can never corrupt array timing.

  • async_fifo.sv — textbook Cummings dual-clock FIFO: (AW+1)-bit binary+Gray pointer pairs, 2-flop synchronizers each direction, registered full (a combinational full would close the loop full→wbin_nxt→wgray_nxt→full), combinational empty from two registered Grays which enables FWFT reads. DEPTH=16, power of two.
  • systolic_ctrl.sv — six states: S_RD pop M samples (latch B rows, push A columns into data_align) → S_WLD N weight-load cycles (rows ≥ M zero-padded) → S_SWP one swap pulse → S_CMP stream N A-rows with in_valid → S_COL capture N result rows as out_valid arrives → S_WR push C rows out with back-pressure.
  • data_align.sv — the bus delivers A by columns but the array eats A by rows; this buffer stores columns and reads rows, zero-padding contraction indices k ≥ M so an N×M operand maps onto the N×N mesh.

Track B: the behavioral DUTs used in the UVM run

For the UVM deliverable the DUTs are the simplest models that honor the interface contract — the TB cannot tell the difference, sims run in seconds, and EDA Playground setup stays trivial.

  • systolic_array (behavioral): while in_valid is high, do one rank-1 update per cycle into a 4×4 accumulator (first cycle seeds with c_din). When in_valid drops, latch the accumulator and stream N rows with out_valid, one row per cycle.
  • sub_sys (behavioral): two DEPTH-4 FIFOs built as memory arrays + binary pointers (deliberately not SV queues — see the bug story in the interview tab). The sr_clk process waits for M words, unpacks A/B, computes all of C combinationally in longint arithmetic, holds the four packed rows, and emits them into the output FIFO one per sr_clk cycle, stalling when the output FIFO is full.
// the heart of the behavioral array (one rank-1 update per valid cycle)
if (in_valid) begin
  for (int i = 0; i < N; i++)
    for (int j = 0; j < N; j++)
      acc[i][j] <= accumulating ? acc[i][j] + $signed(a_din[i]) * $signed(b_din[j])
                                : $signed(c_din[j]) + $signed(a_din[i]) * $signed(b_din[j]);
  accumulating <= 1'b1;
end

Assumptions & scope (stated, not hidden)

  • 1 ≤ M ≤ N. M_eff = min(M, N); unused weight rows / activation columns are zero-padded. M>N would need c_dout→c_din loop-back accumulation over ⌈M/N⌉ passes — the port is provisioned, the control is documented as the extension point, not built.
  • Accumulator wraps at 16 bits per the spec; the golden model truncates identically, so checking is bit-accurate even for overflowing inputs.
  • Two implied control strobes (w_load_en, w_swap) added at the array level; the PDF explicitly allows unlisted control signals.
  • Frames are processed sequentially in the RTL controller; the double buffer removes the reload stall, not the drain. Peak “one matrix every M cycles” would need wavefront weight-swapping — documented as an enhancement.
  • Reset is active-low asynchronous, shared by both FIFO domains.

One environment, both DUT levels

A single systolic_env owns three agents (one for the array pins, one per sub-system channel), two instances of the same scoreboard class, three coverage collectors, and a virtual sequencer. Both DUTs are instantiated side by side in tb_top, so any test can exercise either level or both.

In-monitors rebuild each matrix from the pins and publish golden expectations; out-monitors publish observed results; each scoreboard blocks on a pair of TLM analysis FIFOs and compares in order.

Inside coverage_test — the directed list

  • Per-M block (12 items): for each M ∈ {1,2,3,4}, three matrices forcing A[0][0] negative / positive / zero-row — fills cp_m and the entire M × A-sign cross.
  • Sign matrix (9 items): all nine A-sign × B-sign combinations at M=4, using zero-row / zero-column constructions so C[0][0]’s sign is forced too.
  • Magnitude (2 items): |A[0][0]| = 60 (mid bucket) and 120 (large bucket).
  • Overflow (1 item): A row 0 and B column 0 all +127, M=4 → C[0][0] = 4·127² = 64,516 > 32,767 — the 16-bit accumulator wraps and the ovf=yes bin fills; the scoreboard still matches because the golden model wraps identically.
  • Part 2 (12 items): M sweep 1→4 through the sub-system (3 matrices each) to close ss_coverage — write/read strobes, full/empty flags, every M bin on the bus.

  • Square multiply M=N at both levels (smoke).
  • Full-range random signed operands, random M per matrix (sa_random, ss_random, regression).
  • Streams of consecutive matrices with concurrent, independent write and read masters (ss_multichannel).

The closure story

  1. Random tests alone plateaued around 65% on the transaction covergroup.
  2. Hole analysis: zero-sign bins need an entire row/column of zeros (probability ≈ (1/256)4 per matrix); the overflow bin needs near-max operands aligned along a full row and column; magnitude buckets for one fixed element fill slowly.
  3. Response: gen_cov() directed builders (random background + forced row/column patterns), a 24-item directed list on the array, and an M sweep through the sub-system.
  4. Result: all three covergroups at 100.00% in one 9-second run — the checked-in result-3/xrun.log, with coverage database under result-3/cov_work/ and multi-test merging via imc.

Known gaps — stated honestly

  • No SVA protocol assertions (out_valid burst length, FIFO overflow/underflow, dout stability while unread).
  • No reset-during-traffic test; no X-propagation checking.
  • One clock ratio per UVM run; ratio is a one-line edit but not swept automatically.
  • Fixed 200 ns end-of-test drain instead of an objection/phase-ready-to-end handshake.
  • N and DIN_WIDTH are compile-time macros — parameter regression means recompiling, not re-running.
  • The checked-in closure run is single-seed (seed 1); multi-seed soak exists (-svseed random on regression_test) but isn’t archived.

Every one of these has a matching “how I’d improve it” answer in the interview tab — knowing the gaps is half the interview.

Gap analysis: what a PDF-faithful RTL DUT would add

The behavioral models abstract away real hardware behaviors — and tests for those behaviors currently have nothing to bite on. Swap in the real design (pipelined weight-stationary mesh, Gray-pointer async FIFOs, controller FSM) and every row below becomes a required test that none of the nine current tests covers.

Interview preparation

Grouped by the angle an interviewer usually takes. Answers are written the way you’d actually say them — specific to this project, with the numbers ready.

1 · project walkthrough
Give me a two-minute overview of the project.

“The assignment was to verify a systolic-array matrix multiplier at two levels: the bare systolic_array module — N=4, 8-bit signed elements, C=A×B accumulated over M input cycles — and a sub_sys that wraps it with input/output FIFOs across two asynchronous clocks, sys_clk for the bus and sr_clk for compute. I built one UVM 1.2 environment that verifies both DUTs simultaneously: an agent on the array pins, two channel agents on the sub-system bus (write and read, coordinated by a virtual sequence), monitors that rebuild each matrix from the pins and compute a golden result, and one scoreboard class instantiated per level. Three covergroups — transaction math, array pin protocol, bus protocol. Nine tests, smoke through constrained-random through a directed coverage test. The final Xcelium run: 36 matrices, all matched, all three covergroups at 100%, zero errors. I also implemented the optional RTL — a weight-stationary PE mesh with skew registers and a Gray-pointer async FIFO — and verified that separately with Verilator.”

Why is a behavioral model your DUT in the UVM run instead of your own RTL?

The deliverable being graded is the testbench, and the assignment explicitly says RTL is not required. A compact behavioral model that honors the exact interface contract keeps sims fast, keeps the EDA Playground setup reproducible, and decouples TB bring-up from RTL debug — which is exactly how you bring up a UVM env in a real project before RTL is ready. The env can’t tell the difference: swapping in the real RTL is only a tb_top instance change, and the same golden model already regresses that RTL in the Verilator benches.

How did you satisfy the reuse requirement between module level and sub-system level?
  • One matmul_item with the golden compute() serves both levels — the transaction is level-agnostic.
  • One scoreboard class, two instances (sa_sb, ss_sb).
  • One env holds all three agents; one transaction covergroup subscribes to both input monitors.
  • One base_test owns objections, drain, and wait_sb(); each test is ~15 lines.
  • Only the pin-touching pieces (interface, driver, monitor) are per-level — unavoidable, since the physical interfaces differ.
What was the hardest part?

The two-clock flow-control corners. Getting the read driver to pop exactly one word per handshake against FWFT semantics, and making the input monitor count only accepted writes (wr_fifo && !in_fifo_full) so predictions stay aligned with what the DUT actually consumed — otherwise the scoreboard drifts by one matrix under back-pressure and every subsequent compare fails. Off-by-one alignment bugs across clock domains are subtle because everything still “mostly works.”

2 · bugs & debug stories
Walk me through a bug you encountered and how you solved it.

Best one: the sub-system scoreboard reported mismatches where dout was stale by one word. My first FIFO model used a SystemVerilog queue with assign dout = q[0]. On Xcelium, that continuous assignment did not reliably re-evaluate when the queue was mutated inside an always block — dout kept showing the previous head. I debugged it by decoding dout in the monitor against the imem contents in the waveform: the pop visibly happened, the pointer moved, but dout lagged a cycle. Root cause: relying on combinational sensitivity to dynamic-container mutation is implementation-defined territory. Fix: replace queues with a static memory array plus binary read/write pointers — assign dout = omem[ord[AW-1:0]] — pure structural sensitivity that every simulator agrees on. The lesson I quote: when a behavioral model needs a combinational view of its state, keep it to synthesizable-style constructs.

Any other bugs worth telling?
  • Driver/DUT race: the first driver drove vif signals directly at posedge; whether the DUT saw the old or new value that edge was simulator-order luck. Fixed with clocking blocks (output #1, input #1step) — and init_drv() drives idle values through the clocking block so there’s exactly one driver of those nets, never a multi-driver X.
  • Reserved keywords: coverage bins named small/medium/large failed to compile — they’re Verilog charge-strength keywords. Renamed sml/mid/lrg. A thirty-second fix once the error message is read carefully.
  • Silent zero coverage: Xcelium scores nothing without -coverage all; the covergroups just report 0.00%. Baked the flag into the run scripts.
  • VCD tooling: Xcelium emits $scope clocking constructs for clocking blocks that some VCD viewers can’t parse — the dump deliberately excludes interface instances and dumps DUT scopes plus mapping wires instead.
Your scoreboard mismatches. What’s your debug flow?
  1. The scoreboard prints the full got/exp 4×4 grid and the matrix’s M — localize which matrix and which elements differ (one element? a row? everything shifted?).
  2. Decide which side is lying: recompute C by hand from the A/B the monitor captured. If expected is right, the DUT path is suspect; if expected is wrong, the monitor/unpacking is.
  3. Walk the datapath in the waveform, halving the search each hop — sub-system order: was the packed din word correct (driver packing)? did imem capture the right words (write path / full flag)? does hold[i] match golden rows (compute)? does dout pop the right word at the right pointer (read path)?
  4. Pattern-match the symptom: everything shifted by one word → pointer/handshake; single element wrong → arithmetic/packing; sign-flipped values → missing $signed.
How do you know your golden model itself is correct?

Three independent legs: (1) hand-worked examples — two waveform frames recomputed digit-by-digit in the README; (2) redundant implementations — the UVM item’s compute() and the Verilator benches’ matmul_pkg::golden_matmul were written separately and agree; (3) cross-implementation consistency — the same golden matches two structurally unrelated DUTs (a spatial PE mesh and a temporal behavioral loop). A common-mode bug would have to hit all of those the same way, including the overflow-wrap behavior, which the directed overflow test exercises explicitly.

3 · uvm concepts
Why does the monitor compute the expected result instead of the sequence sending it to the scoreboard?

Because then the check covers the whole path. The in-monitor rebuilds A and B from the pins — so if the driver packs the bus word wrong, or drops a beat under back-pressure, the prediction diverges from the stimulus intent and the scoreboard catches it. Sequence-side prediction would happily match a broken driver against a broken DUT stimulus. It also keeps the scoreboard passive and stimulus-agnostic: directed, random, or a future sequence library all get checked identically.

Why uvm_tlm_analysis_fifo in the scoreboard rather than uvm_analysis_imp?

analysis_imp forces a write() callback — you get pushed data in zero time and must build your own queueing and synchronization. uvm_tlm_analysis_fifo gives an unbounded FIFO with a blocking get(), so the run_phase is three lines: get(exp); get(act); compare(). For a strictly in-order DUT that’s the whole ordering problem solved. If the DUT could reorder, I’d switch to keyed matching (associative array on a transaction ID).

Explain the UVM phases you actually used.

build_phase top-down: factory-create children, read config_db (vifs, knobs). connect_phase bottom-up: analysis ports → scoreboard FIFOs, driver seq_item_port → sequencer export, virtual-sequencer handles. run_phase: the only time-consuming phase here — base_test raises an objection, runs the test’s sequences, waits for the scoreboard count, drains 200 ns, drops the objection. report_phase: scoreboards print PASSED/FAILED/IDLE, covergroups print percentages. I’d name-drop that a cleaner drain uses phase_ready_to_end with an outstanding-transaction check instead of a fixed delay.

How does uvm_config_db work in your bench, and what are its gotchas?

tb_top publishes both virtual interfaces with set(null, "*", "sa_vif", said); drivers/monitors/coverage get them in build_phase and uvm_fatal on failure. The back-pressure test sets read_delay targeted at "env.ss_rd_agt.drv" before super.build_phase so it exists before the driver is built. Gotchas worth saying: set-before-get ordering, precedence (higher/later setters win), wildcard scoping surprises, and the type must match exactly — int vs int unsigned lookups miss silently.

Where would the UVM factory actually help you here? Give a concrete override.

Error injection without touching the env: class sa_err_driver extends sa_driver, override drive() to corrupt one beat or glitch in_valid mid-frame; then in a test’s build_phase: set_type_override_by_type(sa_driver::get_type(), sa_err_driver::get_type()). Because every component is created via ::type_id::create, the env silently builds the error driver. Same trick swaps in an item subclass with tighter constraints for a stress test.

Explain your virtual sequence. Why is it needed?

The sub-system has two independent masters — someone writing operands and someone draining results — that in reality don’t coordinate. ss_vseq (running on a virtual_sequencer that holds the three sequencer handles via `uvm_declare_p_sequencer) forks a matrix_seq on the write sequencer and a read_seq of N×num_matrices pop-tokens on the read sequencer, join-ing both. Because they genuinely race, FIFO occupancy varies run to run — which is precisely how the full and empty coverage bins get hit without being scripted.

What are objections for, and what’s your end-of-test strategy?

Objections keep run_phase alive: the test raises one, and the phase can’t end until it drops. My base_test raises, runs sequences, then blocks on wait_sb(sb, n) — the scoreboard must have processed n matrices, not merely have had them driven — then a 200 ns drain, then drop. Plus a 2 ms watchdog in tb_top that uvm_fatals so a hung handshake fails loudly instead of running forever. The honest critique I’d volunteer: the fixed drain is a magic number; production style is objection-per-transaction or phase_ready_to_end.

uvm_subscriber — what is it and why use it for coverage?

A component with a built-in analysis_export and an abstract write() — the natural sink for an analysis port. matmul_coverage extends uvm_subscriber#(matmul_item): both in-monitors connect to it, write() extracts sampled attributes into ints and calls cg.sample(). Coverage stays out of monitors (which observe) and scoreboards (which check) — three components, three single responsibilities, and the covergroup automatically sees stimulus from both DUT levels.

4 · systemverilog & tb mechanics
Explain clocking blocks. What do #1step and output #1 mean?

A clocking block binds signals to a clock edge with explicit sampling and driving skews. input #1step samples in the Preponed region — the value just before the edge, i.e. the stable pre-edge state, immune to same-edge NBA updates. output #1 drives 1 ns after the edge, so the DUT’s flops sampled the old value and see the new one next edge. Together they make TB↔DUT races structurally impossible — which I can testify to, because the first driver revision without them had exactly that race. One subtlety I handled: initializing pins through the clocking block (init_drv()) rather than assigning the raw nets, to keep a single driver.

What signed-arithmetic pitfalls did you have to handle?
  • A product of two 8-bit signed values needs 16 bits, and summing M of them needs headroom — golden accumulates in longint, then truncates to 16 to mirror the hardware wrap.
  • In SV, if any operand in an expression is unsigned, the whole expression goes unsigned — the bus unpacking therefore wraps every slice in $signed(...) before multiplying.
  • Overflow detection: sign-extend the truncated C[0][0] back to 64 bits and compare with the full-precision accumulator — inequality means the wrap changed the value, which sets the ovf coverage attribute.
  • Comparisons in the scoreboard use !== so an X in the observed data fails instead of X-matching.
Queues vs. memory arrays for modeling a FIFO — when does it matter?

Queues are perfect for scoreboard-side buffering (my TLM FIFOs are queues underneath). They bite when a continuous assignment must reflect their state — comb sensitivity to dynamic-container mutation is where simulators disagree, which is the stale-dout bug I hit on Xcelium. A static array plus pointers has plain structural sensitivity, works everywhere, and as a bonus models occupancy honestly: full = (wr_ptr - rd_ptr) ≥ DEPTH with (AW+1)-bit pointers, exactly like real hardware.

Why interfaces at all? And why is rst_n an interface signal rather than in a clocking block?

Interfaces bundle the pins, the clocking blocks, and modports into one handle that crosses the static/class boundary as a virtual interface through config_db — without them every driver would need a hierarchical path. rst_n stays a plain interface signal because reset is asynchronous by definition; the driver does wait (vif.rst_n === 1'b1) — with === because at time 0 the net is X, and I want “really 1,” not “not 0.”

Your parameters are macros (`DW, `NN). Defend that, and what’s the better way?

Macros give one shared compile-time geometry across interfaces, classes, and DUT instantiation with zero plumbing, which fits a fixed-configuration assignment. The cost: changing N means recompiling, and classes can’t be reused at two geometries in one sim. Production style: package localparams driven by compile defines for the static world, plus a uvm_config object carrying geometry for the class world, with items using dynamic arrays sized from it. Then a Makefile matrix regresses (N, DIN_WIDTH, clock ratio) combinations — that’s my named improvement for requirement 3.

5 · cdc & fifos
Why Gray-code pointers in an async FIFO?

A multi-bit binary pointer crossing domains can be captured mid-transition — several bits changing means the synchronizer can latch an arbitrary garbage value. Gray code changes exactly one bit per increment, so the synchronized pointer is always either the old or the new value — a valid, merely stale pointer. Flags computed from a stale pointer err conservative: full asserts a touch early, empty asserts a touch early — you lose a beat of throughput, never data.

Why are the pointers AW+1 bits for a 2^AW-deep FIFO?

With AW bits, full and empty are both “pointers equal” — indistinguishable. The extra MSB acts as a wrap/lap counter: empty is complete Gray equality; full is the Cummings condition wgray_next == {~rgray_sync[AW:AW-1], rgray_sync[AW-2:0]} — same position, opposite lap (top two Gray bits inverted).

In your RTL FIFO, why is full registered but empty combinational?

full feeds the write-pointer increment; a combinational full closes the loop full → wbin_next → wgray_next → full. Registering it breaks the loop, is the canonical Cummings form, and can only err conservative. empty compares two already-registered Gray values — no loop — and keeping it combinational is what enables first-word-fall-through: rdata shows the head the same cycle a word lands, and rd_en just pops.

Your behavioral sub_sys compares binary pointers across the two clocks. Isn’t that a CDC violation?

Yes — and I’ll say so before the interviewer does. in_fifo_full combines a sys-domain and an sr-domain binary pointer with no synchronizer; in silicon that’s a real bug. It’s acceptable only because this is a zero-delay functional stand-in: an event-driven simulator has no metastability, so the model still behaves like an ideal FIFO. The synthesizable answer exists in the same repo — the Gray-pointer async_fifo in the RTL track. Knowing exactly where a model is allowed to cheat, and saying it out loud, is the point of the question.

How would you verify CDC properly?
  • Structural: CDC lint (Spyglass CDC / Questa CDC) — every crossing has a recognized synchronizer, no reconvergence of synced bits, no un-synced multi-bit buses.
  • Dynamic: sweep clock ratios and phases including nasty near-integer ratios, add jitter; run long soaks where FIFO occupancy repeatedly saturates both ways.
  • Assertions: Gray pointers change at most one bit per own-clock edge; FIFO never writes when full or pops when empty; data written equals data read (in-order integrity).
  • Reset: verify both domains come out of reset cleanly in either order — tied to my named gap of no reset-mid-traffic test.
6 · systolic-array architecture
Why a systolic array for matrix multiply at all?

Data reuse with purely local wiring. Every operand fetched from memory is used N times as it marches through the mesh, so bandwidth drops by ~N versus a MAC farm hitting SRAM every cycle; wires are nearest-neighbor only, which is what makes the layout scale. N² PEs retire N²·M MACs in about M + 2N − 1 cycles — near-perfect utilization for streamed back-to-back matrices. It’s the TPU / TetraMem-style architecture for exactly this workload.

Weight-stationary vs. output-stationary — what is this design and what else exists?

The RTL is weight-stationary: PE(r,c) pins B[r][c] in place, activations stream left→right, partial sums trickle top→bottom, and column c spatially reduces Σr A[i][r]·B[r][c]. Alternatives: output-stationary (C accumulates in place; A and B both stream — the page-11 module interface actually fits this view, which is what my behavioral model implements temporally) and row-stationary (Eyeriss; optimizes convolution reuse). Being able to say the RTL and the behavioral model realize two different dataflows that provably compute the same C is a strong moment in this interview.

Why must inputs be skewed, and where does the 2N−1 latency come from?

PE(r,c) needs activation a[i][r] to arrive together with the partial sum of row i that has already accumulated r hops above it — so row r’s input is delayed r cycles, forming the classic diagonal wavefront. At the bottom, column c’s result finishes c cycles later than column 0, so a matching N−1−c de-skew realigns whole rows. Total: N−1 (skew) + N (mesh traversal) — out_valid is in_valid through a 2N−1 shift register, which is also exactly how the TB knows when to collect.

Explain the double-buffered weights and what problem they solve.

Loading B costs N cycles; naively the array idles during it, halving throughput on alternating load/compute streams (the page-10 problem). Each PE therefore holds two weight registers — w_load written row-by-row while w_active keeps computing, and a one-cycle swap_w promotes the new set. The reload stall vanishes. Remaining honesty point: the swap is still global, so a frame must drain before swapping — per-column wavefront swapping is the documented next step to true peak throughput.

What happens if M > N? How would you support it?

The mesh only holds N contraction slices, so M>N needs multi-pass accumulation: slice A into ⌈M/N⌉ column-blocks and B into row-blocks, and seed each pass’s partial sums with the previous pass’s results — that’s precisely what the c_din port exists for (c_dout→c_din loop-back). Structurally provisioned, control not implemented; both DUT and monitor clamp M to N, and the limit is a stated assumption. Verification impact if built: sequences spanning passes, golden unchanged, plus new corners — partial-sum wrap between passes and back-pressure landing mid-accumulation.

Why does one covergroup treat magnitude buckets and signs of a single element as meaningful coverage?

It’s a proxy model, and I’d present it as such. Signed-datapath bugs cluster at sign boundaries and near the representational edges, so signs {neg, zero, pos} × both operands, magnitude buckets up to ±127, and the wrap bin target the risky regions with 40 bins instead of thousands. Element [0][0] is the sampled proxy — the directed generator constructs matrices so the proxy is forced through every case. The stricter model — sample all N² elements, cross with M — is in my improvements list; it costs simulation and closure effort and buys mostly redundant evidence for a uniform datapath.

7 · coverage & closure
Random coverage plateaued. Walk me through what you did.

It stalled around 65%. First, hole analysis — which bins are empty and why: the zero-sign bins need an entire A row or B column to be zero, probability (1/256)⁴ per matrix — effectively never; the overflow bin needs near-max operands aligned along a full row–column pair; the magnitude buckets of one fixed element fill slowly. Then the fix matched the cause: a gen_cov() directed builder (random background, forced row/column patterns, five modes) and a 24-item directed list that closes every remaining bin deterministically, plus an M sweep through the sub-system for the bus covergroup. One 9-second run, three covergroups at 100%. The principle: random for breadth, directed for the measure-zero corners — and coverage feedback is what tells you which is which.

Coverage is 100%. Is the design verified?

No — 100% means my model of interesting is exhausted, and the model is the weak link. What it doesn’t capture: temporal corners (reset mid-frame, M changing while data is in flight), clock-ratio sensitivity, all-elements sampling, cross of back-pressure with M. Also: functional coverage without code coverage can hide unexercised RTL; on real RTL I’d require line/expression/toggle/FSM closure too (the log shows -coverage all already collects it). The mature answer: coverage closure is exit criteria for the plan; the plan itself gets reviewed against the spec, and the gaps I listed are the review.

How would you run this as a real regression?

The pieces exist: run.sh for one test, run_all.sh loops the nine tests with -covtest per test and merges databases with imc -exec merge_cov.tcl. Scale-up: multi-seed nightly (-svseed random, archive seeds so failures reproduce), a compile matrix over (N, DIN_WIDTH, clock ratio), rank tests by coverage contribution, gate merges on zero UVM_ERROR, and trend the merged number in CI rather than trusting one run.

8 · improvements & critique
What are the improvements you’d make to this UVM testbench?

In priority order, each tied to a real gap:

  1. SVA protocol assertions, bound into the interfaces: out_valid bursts are exactly N cycles; never write-when-full or pop-when-empty; dout stable while unread; Gray pointers change one bit per edge. Assertions catch protocol bugs the scoreboard’s end-to-end view can blur.
  2. Reset and error stimulus: reset mid-frame with clean-recovery checks; in_valid gaps inside a frame; illegal M_minus_one driven on purpose (today the clamp is defensive code that no test provokes).
  3. Parameter/clock regression: geometry into a package + config object, Makefile matrix over (N, DIN_WIDTH, sys:sr ratio) including the inverted ratio — the UVM run currently fixes 10:14.
  4. End-of-test hygiene: replace the 200 ns drain with phase_ready_to_end keyed on outstanding scoreboard items.
  5. Richer coverage: all-elements sign sampling, FIFO occupancy bins, back-pressure × M cross, clock-ratio covergroup.
  6. Cycle-accurate predictor (the assignment’s “big plus”): model the 2N−1 latency and FIFO timing so the TB checks when, not just what — catches performance regressions functionally-correct runs hide.
  7. Swap the behavioral DUT for the track-A RTL in the UVM run and close code coverage on it; scoreboard out-of-order tolerance via keyed matching as a robustness upgrade.
  8. Infrastructure: multi-seed CI with archived seeds, coverage trend dashboards, DPI-C golden model if C++ ever becomes the reference.
Be critical: what are the weaknesses of your testbench?

Volunteering these before being asked is the move: no assertions; no reset-during-traffic test; one clock ratio per run; single-seed archived closure evidence; a magic-number drain; compile-time geometry; coverage sampling one proxy element; the behavioral DUT’s deliberate CDC shortcut; M>N unsupported by stated assumption. None are unknowns — each has a named fix in my improvements list, which is the difference between a gap and a blind spot.

9 · curveballs
The DUT starts emitting matrices out of order. What breaks, and how do you fix it?

My scoreboard’s blocking in-order compare fails on the first swap. Fix: keyed matching — carry an ID (or hash of A,B,M) with the expected item, store expectations in an associative array, match observations by key, and add a timeout for never-matched entries. The monitors don’t change; only the compare loop does — which is the payoff of keeping prediction in monitors and policy in the scoreboard.

FIFO DEPTH changes from 4 to 2, or to a non-power-of-two. Impact?

DEPTH=2: functionally the TB is untouched (the write driver already honors full every beat); back-pressure just triggers constantly — arguably better stress. Non-power-of-two: the behavioral pointer FIFO still works (comparison arithmetic, not bit-wrap), but the Gray-pointer RTL FIFO breaks — Gray adjacency only holds when the pointer wraps at a power of two. Standard practice: round up and cap occupancy, or use credit-based flow control. Also $clog2-derived widths need re-checking. The follow-up they want: full/empty corners move, so re-run back-pressure and re-close the FIFO-flag bins.

sys_clk becomes much faster than sr_clk (say 5:1). What do you expect to see?

The writer outruns the compute engine: in_fifo_full asserts routinely, the write driver spends most beats stalled, and sustained throughput collapses to the sr-side rate of one matrix per ~(M + 2N) sr cycles; the reader mostly polls out_fifo_empty. Correctness must not change — that’s the whole claim of the flow-control design — and the checks that prove it are the driver honoring full, the monitor counting only accepted writes, and (on the RTL) the Gray-pointer conservatism. This is exactly why clock-ratio sweep is on my improvements list rather than hand-waved.

How would you verify the PE by itself? Was the mesh-level TB enough?

I did both. tb_pe unit-tests the cell directly — 807 checks over random a/b/c_in including the ±127/−128 extremes, plus the double-buffer sequencing (load doesn’t disturb the active weight; swap takes effect exactly next cycle). Mesh-level tests can prove sum-correctness while masking a symmetric cell bug or a wiring transposition that unit + mesh together pin down. Small unit benches are cheap; debugging a 16-PE wavefront to find a one-line MAC bug is not.

Your test computes golden C in the monitor at zero time. What if the reference model were slow — a SystemC or DPI-C model?

Move prediction out of the monitor’s sampling path: monitor publishes the raw stimulus item; a separate predictor component (subscriber) calls the DPI/SystemC model — possibly pipelined or threaded — and pushes expectations into the scoreboard FIFO. The blocking-get scoreboard already tolerates arbitrary prediction latency because it just waits on whichever FIFO is behind. That’s the standard predictor-scoreboard split; my current compute-in-monitor is the collapsed version you use when the model is a ten-line function.
